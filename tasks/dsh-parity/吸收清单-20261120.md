## 3. 为什么前几轮像「理解不了」（三个可查的病灶）

1. **把「DSH 有」当成「Atlas 该有」。**
   `B-F02-UPDATE-01…16`（16 条 P1）是 DSH 的 Electron 自动更新器 + 强制更新遮罩 + 飞书策略认证 + 频道切换。
   Atlas 是自用的本地应用，没有发布频道。这 16 条 P1 在「最该先做」的清单里占 13%。
2. **把「符号」当「能力」。**
   `Atlas-DSH-全量统计` 里 81,553 条 DSH 声明中 45,272 条是类型契约、28,842 条标「未定位（类型契约）」。
   TypeScript 的 `ClassDeclaration`/`constructor` 在 Python 里没有对应物可「缺失」。
   `T1-DSH-TOOLTIP-ESCAPE-SEMANTIC-133` 干的就是这种事：一轮解析 19 个语义单元，分母 418,395。
   分母永远追不上 → 每一轮都能「有进展」但永远没有交付物。这是**结构性做不完**，不是模型笨。
3. **不给验收判据，只给「对齐」。**
   一份「补齐：更新轮询调度」的行动项，做完了也说不清哪里变好。没有判据的任务，
   agent 只能靠写回执（receipt）证明自己没偷懒 → 回执越来越长，产品一行没变。

## 7. 本轮施工记录：Windows 写入边界（P0-1）已落地

**代码**

| 文件 | 作用 |
|---|---|
| `core/atlas/windows_acl_sandbox.py` | 写入受限 token + 动态 capability SID + 目标根 DACL 临时授权（用后逐字节还原） |
| `core/atlas/sandbox.py` | 本地执行优先走 ACL 层，后端名写进 `sandbox_backend`；ACL 不可用才退回 Job Object |
| `core/tests/test_windows_acl_sandbox.py` | 四条边界用例（工作区可写/根外不可写/read-only 不可写/ACL 还原） |

**判据（全部实跑通过）**

| 场景 | 结果 |
|---|---|
| `workspace-write` 写工作区 | 成功 |
| `workspace-write` 写工作区外（同一用户拥有的目录） | `拒绝访问`，文件不存在 |
| `read-only` 写工作区 | `拒绝访问`，文件不存在 |
| 读工作区外文件（`C:\Windows\win.ini`） | 正常读出 |
| 子进程 `%TEMP%` | 指向私有 scratch，真实 `%TEMP%` 不被授权 |
| 调用结束后的 DACL | 与调用前 `icacls` 输出逐字相同（`acl_roots_restored=True`） |
| 4 线程并发同一工作区 | 串行化无死锁，4/4 写入成功，ACL 无线程间互相覆盖 |

**踩到的三个真实坑（都已修，别再犯）**

1. `CreateRestrictedToken` 在 `advapi32.dll`，不在 `kernel32`（WinError 87）。
2. 受限 token 缺 Logon SID → 无法接入 `winsta0\default`，子进程 `0xC0000142`。
3. **`SetNamedSecurityInfoW` 回写 DACL 时必须带上原安全描述符的 PROTECTED 位**，否则对象会
   开始继承父目录的 ACE——"还原"变成了"改 ACL"。同理，给根加 ACE 时也要带原位（`GetSecurityDescriptorControl`）。
4. 受限 token 的读写都要**普通 SID 列表与受限列表同时放行**（交集），所以：
   给根加 capability ACE 之外，还要给调用者 logon SID 加只读 ACE（否则 DACL 受保护的根连列目录都失败），
   并在「调用者本来就能写该根」时给用户 SID 补一条满权 ACE（用真实创建+删除测出来，永不越权）。
