# Atlas vs DeepSeek-Harness — what the numbers mean

`BENCH.md` is regenerated by `core/scripts/omni_bench.py` on every run: it holds
raw measured values and nothing else. This file is the reading of them, written
by hand, and it does not move when the benchmark is re-run.

## Result (three passes of 2026-11-15, 7 prompts each)

| Metric | Atlas | DSH | Delta |
|---|---:|---:|---:|
| Prompt tokens per turn (cache included) | 8,900 | 17,377 | **−48.8%** |
| Wall-clock ms per turn, both warm | 3,937–5,218 | 4,282–5,498 | −5% to −8% |
| Wall-clock ms per turn, DSH cold | — | 11,250–12,608 | — |
| Tasks completed | 7/7 | 7/7 | tie |

Both harnesses ran the same seven prompts against `https://d1api.xin/v1` with
model `deepseek-v4.1-flash`, so a difference is the harness, not the model.

## Context: a clear Atlas win on turn one, which erodes

8,900 vs 17,377 tokens for the same single-turn task is a prompt **half the size**.
That is system prompt, tool schemas and history assembly. It means cheaper turns
and more headroom before the window fills.

**But it does not hold.** `MULTITURN.md` measures the same conversation over eight
turns: Atlas starts at 8,039 and grows ~1,600/turn, reaching 19,337 by turn 8;
DSH starts at 17,376 and stays flat because its prefix is cached. The two cross at
roughly turn 8. The single-turn number is a starting advantage, not a permanent one.

## Latency: level, Atlas marginally ahead

Three independent passes, each a full 7-task run with third-party hooks isolated:

| Pass | Atlas median | DSH median (boot excluded) | Margin |
|---|---:|---:|---:|
| 1 | 3,937 | 4,282 | −8.1% |
| 2 | 4,171 | 4,516 | −7.6% |
| 3 | 5,218 | 5,498 | −5.1% |

Atlas was faster in all three, by 5–8%. The direction is consistent, which is why
the claim is "marginally ahead" rather than "level" — but the absolute values drift
by ~30% between passes (gateway latency varies), so the margin is not a precise
figure. Three passes is also not enough to rule out that DSH's boot subtraction is
slightly too generous on a loaded machine.

## Two measurements that almost went wrong

Both were caught by looking at the raw records instead of trusting the first table.

### 1. The 44× phantom win

The first pass reported **225** prompt tokens for DSH against **9,949** for Atlas.
Written up naively that is a 44× Atlas win. It was a unit mismatch:

- DSH's `--json` reports `inputTokens` as the **uncached remainder** and puts the
  rest in `cacheReadTokens`; its own `totalTokens` sums all four buckets
  (`packages/llm/token-meter/src/index.ts:71`).
- Atlas folds cache reads **into** `input_tokens` and records the cached subset
  separately (`core/atlas/usage.py:111`, `cache_hit_rate = cached / input`).

Comparing the raw `input` field put a cached turn's incremental tokens against an
uncached turn's full prompt. `Sample.prompt_tokens` in the benchmark now
normalises per harness. Corrected: **2×, not 44×**.

### 2. The 1.7× phantom loss

Atlas then measured **8,296 ms/turn**, apparently 1.7× slower than DSH. Also wrong,
in the other direction. The cost was not Atlas:

```
hook UserPromptSubmit  984ms  exit=0    context-mode hook codex userpromptsubmit
hook UserPromptSubmit  958ms  exit=2    python D:/MemoryOS/.../hook_user_prompt.py  (file gone)
hook SessionStart      907ms  exit=0    context-mode hook codex sessionstart
hook Stop              891ms  exit=0    context-mode hook codex stop
hook Stop              884ms  exit=2    python D:/MemoryOS/.../hook_stop.py          (file gone)
```

Five hooks from `~/.codex/hooks.json`, ~4.6 s of the 8.3 s turn:

- Three were `context-mode` — a real Node process, real cost, but instrumentation
  for **Codex**, not part of Atlas.
- Two pointed at `D:/MemoryOS/adapters/codex/hooks/*.py`, which does not exist on
  this machine, so every turn paid a full Python start in order to fail.

Both were dealt with rather than excluded:

1. **Fixed in Atlas.** `_missing_script` (`core/atlas/runtime/hooks.py`) refuses a
   hook whose declared script is absent and returns exit 127 in 0 ms instead of
   spawning an interpreter that can only fail. That removed ~2.9 s/turn on this
   machine. Covered by `core/tests/test_hook_missing_script.py` (7 tests).
2. **Isolated for measurement.** `omni_bench.py --isolate-hooks` writes a temporary
   `data/hooks.toml` disabling the third-party hooks, then deletes it in a
   `finally` block. The user's own configuration is never edited, and the
   as-installed number (8,296 ms) is kept in this file so the difference stays
   visible.

## Configuration comparison

| Configuration | Atlas ms/turn | Note |
|---|---:|---|
| All `~/.codex/hooks.json` hooks active | 8,296 | what this machine did before the fix |
| Hook fix only (missing scripts skipped) | 5,125 | measured live before the override |
| Hook fix + third-party hooks off | 3,937–5,218 | the architecture-only number (three passes) |

The remaining gap between rows two and three is someone else's Node process, not
Atlas.

## What is still not measured

The benchmark covers single-turn chat, file listing and one shell round-trip.
`MULTITURN.md` adds an eight-turn conversation. Neither measures:

- Long-horizon agentic runs (many sequential tool calls)
- Recovery behaviour (a tool failure mid-run)
- Memory / personalisation quality
- Contexts long enough to force compaction

Those are the areas where a personal assistant actually lives, and no claim in this
document extends to them.
