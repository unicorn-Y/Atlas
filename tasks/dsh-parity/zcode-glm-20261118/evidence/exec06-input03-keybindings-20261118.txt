C. 差距(相对 DSH)
================================================================================
G1 无 revision 乐观锁:GET 返回 mtime,但 PUT 不接受 expected revision;
   两个窗口并发保存 = 后写覆盖,无 409。
G2 非原子写:PUT 直接 write_text;进程崩溃/磁盘满可能留下截断 JSON,
   下次 GET 422,用户丢失全部改绑(DSH 是 writeFileAtomic)。
G3 无跨窗口/跨进程广播:渲染层 3s 轮询 mtime;另一窗口改绑最多延迟 3s,
   且可能被本窗口下一次保存覆盖。
G4 渲染层 UI 保存只写 localStorage,不 PUT 到 keybindings.json;
   文件真源只能被外部写入后轮询应用(单向),编辑与文件持久化未闭环。
G5 无 DSH 的录制态/allowPaste 策略/单写者事务错误回编辑 UI 的契约。

D. 验收标准(二值)
================================================================================
A-1 PUT 接受 `expected_updated_at`;与当前 mtime_ns 不一致 → 409 且不写文件;
    一致 → 原子写(temp+os.replace,文件 0600/目录 0700)并返回新 updated_at。
A-2 GET/PUT 并发测试:两个写者同一基线,第一个成功、第二个 409;
    409 后文件内容仍是第一个写者的完整值(无截断)。
A-3 崩溃/中断测试:在临时目录模拟写一半,恢复后 JSON 可解析(原子写保证)。
A-4 UI 保存路径:ShortcutsPanel 改为 PUT(带 expected_updated_at);409 时显示冲突
    并允许重载/覆盖;成功后其他窗口 ≤1s 内应用(广播或短轮询)。
A-5 复验:pytest 路由测试(GET/PUT/409/422/原子性)+ vitest ShortcutsPanel 冲突路径;
    真机两窗同时改绑一次。
