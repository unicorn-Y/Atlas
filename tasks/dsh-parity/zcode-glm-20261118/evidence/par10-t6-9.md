## 4. 真实平台缺口与最小修复

**缺口复现（修复前，真实句柄，非模拟 remove）**：`2a` 状态在 holder 释放后执行 retry create，返回 **409 `recovery_required`**（预期 200），`cleanup_error`：

```
remove: ValueError: fatal: not a git repository (or any of the parent directories): .git;
worktree still registered: <...>\.atlas-worktrees\repo\<short>;
worktree directory still exists: <...>;
branch still exists: atlas/<short>-metadata
```

证据 `logs/13-prefix-real-lock-tests.txt`（exit 1，`1 failed, 2 passed`）。

**根因**：`git worktree remove --force` 在删除被持文件失败前，已删除 checkout 的 `.git` 文件并留下 damaged admin entry；`WorktreeService.remove` 无法再校验该树，`_worktree_registry_paths()` 仍把它列为 prunable registration，因而跳过 orphan 分支；现有 prune 只在“目录已不存在”分支执行，恢复永远失败。

- `_cleanup_worktree_residue(..., allow_prune: bool = False)`；默认 False。
- 删除失败且目标仍在 registry 时，若 `allow_prune`：执行 `git worktree prune` 并重读 registry；仅当目标从 registry 消失才进入既有 orphan 清理（再次 `validate()`、只删 canonical 受管目录、再 `branch -D`）。prune 不删除有效 registration，因此“忙但完整”的树仍如实失败。

## 6. 平台边界 / 未覆盖

- **`git worktree remove` 的删除顺序是平台事实**：git 2.55.0.windows.3 先删 admin entry，再递归删 checkout。因此“仅 checkout 内文件被持”时 Git 不再 `worktree list` 列出残留（它是未注册 orphan，不是 listed residue）；要复现任务书写的“Git 仍列残留”，必须再有真实句柄持住 admin `gitdir`，形成 prunable registration（测试 `2a/2b`）。两种都是真实 OS 行为，未用 monkeypatch 伪造；回执不把单句柄场景冒充成 listed。
- 单句柄场景下清理仍会删除 branch（`git branch -D` 不触碰被持文件），失败项只剩目录；recovery 行仍记录原 branch，释放后 orphan 清理按记录处理。
- `git worktree prune` 会顺带清理同一仓库中其它真正 stale 的 admin entry；有效/仍被锁的 registration 不会被移除。这是修复的已知副作用边界。
- 记录失败本身仍是注入（`memory.update_conversation` 返回 False），以触发 create 回滚；**清理失败是真实文件句柄导致**，不是注入。未制造真实 DB 写失败。
- 验证面是真实 FastAPI router（`httpx.ASGITransport`）+ 真实 `MemoryStore` + 真实 `git init -b main` 临时仓库，未启动完整 uvicorn/桌面产品。
- 新测试的临时仓库位于候选工作树 `.tmp` 内、外层仍是 D:\Atlas 工作树；测试用 `GIT_CEILING_DIRECTORIES=<tmp_path>` 阻止 git 向上发现宿主仓库，保持产品视角。生产环境若把 workspace 放在另一仓库内部，孤儿目录的 branch 探测可能发现外层仓库——该场景本包未覆盖，保留为边界。
- 最终 link/身份检查与 `git worktree remove`/`shutil.rmtree` 之间仍有 check-then-act 窗口（Windows 无 dirfd 原子句柄）；本包未改变此性质，仍靠 canonical path、精确 assigned-path 等值与删除前复验。
- GET `/worktree/recovery` 仍只读 `exists()`，不做归属校验（沿用 D2 语义，非本包修复对象）。
