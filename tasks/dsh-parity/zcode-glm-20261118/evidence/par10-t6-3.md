## 2. 三节点根因（已判明）

三个节点在 **060071ab 基线**和 **仅含 T5 改动** 的树上同样失败，失败点逐条一致：

| 节点 | 基线失败点 | 根因 |
|---|---|---|
| `test_stdio_session_shutdown_exits_its_real_child` | 第 93 行 `get_server_names() == []` | 夹具把 `await client.start()` 当作“启动完成”。产品 `MCPClient.start()` 是 fire-and-forget：为每个服务器 `create_task(_connect_server)` 后立即返回（`mcp_client.py:595-602` 注释明确“slow handshakes must not delay the first conversation”）。断言时握手还没开始。 |
| `test_cancelled_mcp_discovery_stops_its_real_stdio_child` | 第 137 行 `DID NOT RAISE CancelledError` | `start_task = create_task(client.start())` 早已正常返回；真正持有 transport/子进程并阻塞在 `list_tools` 的是内部 per-server `_connect_server` 任务。取消一个已完成任务不会抛 `CancelledError`。 |
| `test_cancelled_owner_does_not_skip_other_server_cleanup` | 第 175 行 `assert 0 >= 1` | 同一语义错误：`await client.start()` 返回时两个子进程尚未 spawn，立即断言 children ≥ 1 必然失败。 |

证据：
- 基线完整失败日志：`evidence/par10-t6-3-lifecycle-baseline060071ab.txt`（3 failed, 5.61s；日志仅见 `mcp.starting`，无 `server_ready`）。
- 仅 T5 产品代码、未修夹具：`evidence/par10-t6-3-lifecycle-t5code-prefix.txt`（同样 3 节点、同样三行）。
- 最小复现即上述两条：`await client.start()` 返回后立即读取状态/子进程，状态为 `starting`、`get_server_names()` 为空；等待到 `connected` 后两者均成立。

**结论：这是基线夹具的等待语义错误，不是产品关闭缺陷。** 因此不改产品代码；修正等待条件并保留原断言。

5. 节点 3（多服务器清理）：`await client.start()` 后等待 `{"first","second"} == connected`，保留原断言两子进程存在；
   随后仍是取消 `first` 的 `_owner_task`、`stop()`，断言两子进程退出且
   `{"first": "stopped", "second": "stopped"}`（status 保留且结算）。

时点覆盖（对应任务书的准备/启动中取消/已连接停止/多服务器清理）：
- 准备与已连接停止：节点 1（connected 后 stop；owner 任务身份 + 真实 PID 退出）。
