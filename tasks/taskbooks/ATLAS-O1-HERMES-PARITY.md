# ATLAS-O1：对标 Hermes 优化——做到能正常用，和 Hermes 真正同等或更强

> 前提：X2、X4 验收通过。
> 用户要求（2026-10-02）：「优化成能正常用的，要求做到和 hermes 真正同等水平，或者比 hermes 强」。
> 以源码对照和假模型对照为主；真实模型只在第 6 节少量使用，开始前先问用户。外部功能里除了 X2、X4，其余（X1、X3、X5–X7）都不在本波范围内。

## 本波目标

1. **能正常用**：Atlas 在笔记本（Atlas 自己的电脑）上常驻运行；用户每天拿它干真实的活，不崩、不卡、不丢东西，出错能自己恢复，提示看得懂。
2. **和 Hermes 真正同等或更强**：用同一个模型、同一批任务，比 Atlas 和**原版 Hermes**（官方最新版，桌面端 + CLI）。凡是 Hermes 能做好、Atlas 做不好的，都要修到不输。Hermes 有、而 Atlas 范围内该有的功能，都要能用。

## 1. 方法（用户 2026-10-02 确认：能用源码比的就用源码比）

Atlas 的内核就是 Hermes 的 fork，所以 Atlas 只可能在四类地方不如 Hermes，都能从源码里逐项找出来：
- Hermes 的功能被关掉了，或者没接上；
- Atlas 改了 Hermes 的行为；
- Hermes 桌面端有、Atlas 界面没有；
- 同样的输入两边跑出不同的结果。

**以源码对照 + 假模型对照为主，零成本**；真实模型只在最后做少量确认（第 6 节）。

需要用户准备的只有第 6 节那点：一个模型、一个很小的预算。

## 2. 第一块：把 Atlas 在笔记本上装成常驻（「能正常用」的前提）

- 笔记本的开发环境重建：Python 3.14 的 venv、`pip install -e` 本地的 Hermes fork 和 `core`、前端依赖。如果 R1 之前的打包已经能用，也可以直接用安装包版。
- **开机自启**：后台常驻（Hub）随系统启动；断网、睡眠唤醒、模型服务出错后能自动恢复。
- **主机能连过来看**：主机先通过 SSH 隧道看到界面并派活。完整的设备互联属于 X3，以后做。
- 写一份操作说明 `docs/user/laptop-host.md`。

## 3. 第二块：源码对照（Hermes 有的，Atlas 都要能用）

列一张总表，覆盖 Hermes 的全部这些东西，每一项标上：主体 / X2 / X4 / 其他外部功能（以后做） / 不适用。

| 对照对象 | 位置 |
| --- | --- |
| 工具 | `toolsets.py`（`_HERMES_CORE_TOOLS` 等）、`tools/registry.py` 的注册 |
| 斜杠命令 | `hermes_cli/commands.py`（约 100 条） |
| 桌面端调用的后端方法 | `tui_gateway/methods_*.py`、`tui_gateway/contracts/` |
| 桌面端的功能 | `apps/desktop/src`，尤其是 `hermes-parity.test.ts` 自己列的功能清单 |
| 配置项 | `cli-config.yaml.example`、`hermes_cli` 的默认配置 |
| 插件钩子 | `hermes_cli/plugins.py` 的 `VALID_HOOKS` |

标「主体 / X2 / X4」的每一项，在 Atlas 代码里找到对应的实现，结论分四种：
1. 接通了，行为相同；
2. 接通了，但 Atlas 改了行为：要写清楚好在哪；说不清的，改回 Hermes 的做法；
3. 没接通：接上；
4. 故意不做：写明理由，比如安全审查由用户负责。

**Atlas 的改动逐处审一遍**：`core/atlas/engine/` 下所有覆盖或包装 Hermes 行为的地方，包括工具注册覆盖、权限插件、提示词、压缩设置、事件桥，以及 fork 的 `atlas` 分支相对上游的全部 diff。

## 4. 第三块：假模型对照（同一份脚本，两边各跑一遍）

1. 写一个对照框架 `tests/o1/differential/`：同一套假模型脚本，一边用原版 Hermes 的 `AIAgent` 跑（直接用上游代码，不带 Atlas 的插件），一边从 Atlas 的 WebSocket 发起跑。
2. 每个场景记录并比较这些：
   - 发给模型的请求：系统提示词、工具定义、消息列表、压缩后的上下文；
   - 工具调用和工具结果；
   - 出错恢复的过程；
   - 最终的回复和文件改动。
3. 场景至少 20 个：
   - 多轮工具调用、长对话自动压缩、手动压缩；
   - 编辑容错、读大文件分页、搜索、后台进程通知；
   - 插话、停止、撤回；
   - 子 Agent 并行、计划模式、Goal；
   - 模型返回 429 或 500、输出被截断后续写、空回复；
   - MCP 工具；
   - 浏览器操作（X2）、技能安装后使用（X4）；
   - Windows 专项（PowerShell、CRLF、中文路径）。
4. 两边不一样的地方逐个判断：Atlas 更好的，写明理由并保留；Atlas 更差或者说不清的，修好。

## 5. 第四块：用 Hermes 自己的测试检查 Atlas

把 Hermes 的相关测试（`tests/agent/`、`tests/tools/` 里文件、终端、压缩、委派、MCP、浏览器、电脑操作、技能市场）在挂上 Atlas 插件和工具层的环境里跑一遍：
- 原版能过、挂上 Atlas 就失败的，是 Atlas 弄坏的，必须修；
- Windows 上原版本来就过不了的，沿用 C1R 的判断。

## 6. 第五块：少量真实确认 + 日常浸泡

- **真实模型确认**（开始前先问用户，用用户指定的模型，预算很小）：挑 5 个任务，Atlas 和原版 Hermes 各跑 1 次。挑能代表日常使用的：修一个 bug、长任务触发压缩、浏览器三步操作、装一个技能用一次、中途插话。重点看源码和假模型看不出来的东西：
  - 按模型写的提示词实际效果好不好；
  - 首字出现的时间；
  - 真实服务的出错恢复。
- **日常浸泡**：用户正常使用 Atlas 2 到 3 天，或者用假模型脚本模拟每天的工作，收集：
  - 崩溃日志；
  - 卡顿的地方；
  - 内存和句柄变化；
  - 看不懂的提示；
  - 需要手动干预的次数。

## 7. 修，直到不输

1. 把第 3 到第 6 块发现的问题列成清单，每一项写清：现象、Hermes 怎么做的、Atlas 差在哪、怎么修。
2. 修复交给 Luna（high）子代理，按文件分工并行；**能直接用 Hermes 现成实现的，就直接用**。
3. **达标标准**：
   - 源码对照表里「主体 / X2 / X4」的每一项，都是结论 1，或者是理由成立的结论 2、结论 4；
   - 假模型对照的 20 个以上场景，没有 Atlas 更差的；
   - Hermes 自己的相关测试，在挂上 Atlas 之后不新增失败；
   - 5 个真实确认任务，Atlas 都不输 Hermes；
   - 浸泡期间不崩溃，也不需要用户手动修数据。
