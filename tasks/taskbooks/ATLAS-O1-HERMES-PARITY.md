# ATLAS-O1：对标 Hermes 优化——做到能正常用，和 Hermes 真正同等或更强

> 前提：X2、X4 验收通过。
> 用户要求（2026-10-02）：「优化成能正常用的，要求做到和 hermes 真正同等水平，或者比 hermes 强」。
> 这一波**要用真实模型**，要花钱，需要用户参与（第 1 节）。外部功能里除了 X2、X4，其余（X1、X3、X5–X7）都不在本波范围内。

## 本波目标

1. **能正常用**：Atlas 在笔记本（Atlas 自己的电脑）上常驻运行；用户每天拿它干真实的活，不崩、不卡、不丢东西，出错能自己恢复，提示看得懂。
2. **和 Hermes 真正同等或更强**：用同一个模型、同一批任务，比 Atlas 和**原版 Hermes**（官方最新版，桌面端 + CLI）。凡是 Hermes 能做好、Atlas 做不好的，都要修到不输。Hermes 有、而 Atlas 范围内该有的功能，都要能用。

## 1. 用户要准备的

1. 在笔记本上装好最新的原版 Hermes（桌面端和 CLI），和 Atlas 配同一个模型（默认是用户现在的中转模型，或者用户另外指定）。
2. 给出预算上限（金额或 token 数）。超了就停下来报告。
3. 模型的密钥由用户自己填，不发给 Agent。

## 2. 第一块：把 Atlas 在笔记本上装成常驻（「能正常用」的前提）

- 笔记本的开发环境重建：Python 3.14 的 venv、`pip install -e` 本地的 Hermes fork 和 `core`、前端依赖。或者直接用安装包版，如果 R1 之前的打包已经能用。
- **开机自启**：后台常驻（Hub）随系统启动；断网、睡眠唤醒、模型服务出错之后，能自动恢复。
- **主机可以连过来看**：在局域网里用浏览器访问笔记本上的 Atlas（只读查看加派活）。如果这一块牵扯太大，就先保证主机能通过 SSH 隧道看到界面。完整的设备互联属于 X3，以后再做。
- 写一份操作说明 `docs/user/laptop-host.md`。

## 3. 第二块：功能对照（Hermes 有的，Atlas 都要能用）

1. 做一张对照表，来源有四处：
   - Hermes 桌面端 `apps/desktop/src`（里面有 `hermes-parity.test.ts`，可以参考它自己列的功能清单）；
   - Hermes 的斜杠命令表 `hermes_cli/commands.py`，约 100 条；
   - Hermes 的工具集 `toolsets.py`；
   - Hermes 官方文档的功能页。

   每一项标上：主体 / X2 / X4 / 其他外部功能（以后做） / 不适用。
2. 标「主体」「X2」「X4」的每一项，在 Atlas 里实际走一遍，结果分三种：能用 / 能用但比 Hermes 差 / 不能用。后两种全部修好。
3. 对照表写进结果文件，并在 CORE-PARITY 里新增一节「Hermes 对照」。

## 4. 第三块：同模型实测对比（真实模型）

- 任务集 15 个，放在 `tests/o1/tasks/`，每个任务包括起始快照、`task.md`（中文）、`check` 判定脚本、`rubric.md` 人工评分要点。覆盖：
  - 修 bug、加功能、读大仓库回答问题、重构；
  - 长对话（8 轮以上）、必然触发压缩的长任务；
  - 子 Agent 并行、计划后执行、撤回重来、中途插话；
  - Windows 专项（PowerShell、CRLF、中文路径）；
  - 浏览器任务（X2）、电脑操作任务（X2）；
  - 安装一个技能并用它完成任务（X4）；
  - 出错恢复：模型中途返回 429 或 500。
- **每个任务 Atlas 和 Hermes 各跑 3 次**，比较下面这些指标：

| 指标 | 说明 |
| --- | --- |
| 成功率 | `check` 判定通过的比例 |
| 改错和越界 | 改了不该改的、删了测试、留下垃圾文件 |
| 轮数和工具调用数 | |
| token 和花费 | 含缓存命中率 |
| 耗时 | 含首个字出现的时间 |
| 人工评分 | 1 到 5 分 |
| 体验 | 进度显示是否看得懂、出错后提示是否清楚 |

- 跑测脚本 `tests/o1/run.py`。Hermes 用它的 CLI 单次模式跑；需要桌面端的任务（浏览器、技能）用户配合手动跑，或者用它的 TUI 或 JSON-RPC 驱动。

## 5. 第四块：日常使用浸泡（真实模型，少量）

用户正常使用 Atlas 2 到 3 天，或者用脚本模拟每天的真实工作：每天 10 个左右的任务，混合编程、查资料、浏览器、定时任务。收集这些数据：
- 崩溃和错误日志、卡顿的地方；
- 内存和句柄的变化；
- 看不懂的提示；
- 「我得手动干预」的次数。

## 6. 修，直到不输

1. 把第 3、4、5 块发现的问题列成清单，每一项写清：现象、Hermes 怎么做的（看它的源码）、Atlas 差在哪、怎么修。
2. 修复交给 Luna（high）子代理，按文件分工并行；**能直接用 Hermes 现成实现的就直接用**，因为它本来就在我们的 fork 里。
3. 修完以后，**只重跑输掉的那些任务**，直到不输为止。
4. 达标标准：
   - 15 个任务里，Atlas 的成功率 ≥ Hermes，花费不高于 Hermes 的 110%；
   - 每一项 Atlas 都不比 Hermes 差，人工评分和体验都不低于 Hermes；
   - 第 3 块对照表里，「主体 / X2 / X4」的每一项都是「能用」，并且不比 Hermes 差；
   - 浸泡期间没有崩溃，没有需要用户手动修数据的情况。

## 7. 交付

- 结果文件 `tasks/results/ATLAS-O1-HERMES-PARITY.result.md`：
  - 功能对照表；
  - 实测总表和逐任务表（改前、改后各一份）；
  - 浸泡数据；
  - 问题清单和每一项的修法、提交号；
  - 花费总计。
- 更新 CORE-PARITY 的「Hermes 对照」一节、PARITY；更新 `docs/user/laptop-host.md`。
- 跑测脚本和任务集保留下来，以后每次大改动后可以重跑，当回归测试用。
