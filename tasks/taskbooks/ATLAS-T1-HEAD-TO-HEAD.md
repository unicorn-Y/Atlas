# ATLAS-T1：真实模型横向实测

> 先读 ROADMAP-TO-PRODUCT、CORE-PARITY。前提：C6 验收通过，CORE-PARITY 全部 ✔。
> **这一波要用真实模型，要花钱，需要用户参与**（第 2 节）。开工前，用户先把第 2 节的准备做完。

## 本波目标

拿同一批真实任务，在 Atlas 和 6 家对手上各跑一遍，量化比较，找出 Atlas 输的地方，生成补做任务书 T1F。

## 1. 参赛者

| 参赛者 | 怎么跑 | 备注 |
| --- | --- | --- |
| Atlas | 后端 WebSocket（脚本）或 `core/atlas/cli.py` | 被测对象 |
| Claude Code | `claude -p "<任务>" --output-format stream-json`（无头模式），在任务目录里运行 | 需要用户的 Anthropic 账号或 API key |
| Codex CLI | `codex exec "<任务>" --json` | 需要用户的 OpenAI 账号 |
| OpenCode | `opencode run "<任务>"` | 可以接任意模型 |
| Pi | `pi -p "<任务>"`，或者 JSON 模式 | 可以接任意模型 |
| Hermes（原版） | `hermes` 的单次模式（看它的 CLI 文档） | 可以接任意模型 |
| ZCode | 只有图形界面，**手动跑**一个子集，6 个任务 | 用户操作 |

具体命令以各家**当月**的文档为准。装不上、跑不了的写进结果文件，不要硬凑。

## 2. 用户要准备的

1. 确认要用的模型和预算。分两条赛道：
   - **A 赛道（同模型，比外层框架）**：所有能接自定义模型的参赛者都用同一个模型。默认用用户现在的中转模型 `openai/deepseek-v4.1-flash`，或者用户另选一个。Claude Code 能不能接这个模型要查文档，接不了就只参加 B 赛道。
   - **B 赛道（各用最强，比实际体验）**：每家用它自己最强的官方模型，例如 Claude Code 用 Opus 5.5，Codex 用 GPT-6.1 Sol；Atlas 用用户能拿到的最强模型。
2. 在测试机上登录好各家的账号，或配好 API key。**密钥由用户自己填进各家的配置，不要发给 Agent。**
3. 给出预算上限，比如总共不超过多少钱、多少 token。超了就停下来报告。

## 3. 任务集（20 个，覆盖主体的各方面）

任务放在 `tests/t1/tasks/<编号>/`：
- 起始仓库或文件快照；
- `task.md`：给 Agent 的原话，**中文**；
- `check.py` 或 `check.ps1`：自动判断成败的脚本；
- `rubric.md`：人工评分要点。

| 编号 | 类型 | 内容（示例，施工时补全成真实可跑的） |
| --- | --- | --- |
| 01–04 | 修 bug | 给一个有失败测试的小项目（Python、TypeScript 各两个），让它修到测试通过 |
| 05–07 | 加功能 | 在中等规模的仓库里加一个小功能，并补测试 |
| 08–09 | 读大仓库回答问题 | 在 Hermes 或 OpenCode 的源码里回答「X 是怎么实现的」，答案能核对 |
| 10 | 重构 | 跨 5 个以上文件改名、搬动函数，不能把测试改坏 |
| 11 | 长对话 | 连续 8 轮追加要求，最后检查前面的约束有没有被忘掉 |
| 12 | 超长上下文 | 任务中途必然触发压缩，考察压缩后能不能接着把活干对 |
| 13 | 运行和调试 | 起一个本地服务、看日志、修启动错误 |
| 14 | 子 Agent 并行 | 三个互不相关的子任务，看能不能并行、汇总得对不对 |
| 15 | 计划模式 | 先出计划，再按计划执行 |
| 16 | 撤回 | 做一半后撤回到某一步，从那里重新做 |
| 17 | Windows 专项 | PowerShell 脚本、CRLF 文件、带中文的路径 |
| 18 | 文档产出 | 读一个目录，生成一份 Word 或 Markdown 报告 |
| 19 | 中途插话 | 运行中插话改需求（脚本模拟：第 N 秒插入） |
| 20 | 出错恢复 | 模型服务中途返回 429 或 500（用代理注入），看能不能恢复 |

每个任务跑 **3 次**，取平均和最好成绩。不支持某项能力的参赛者，比如插话，就记「不支持」。

## 4. 量什么

每个参赛者、每个任务都记下：

| 指标 | 怎么量 |
| --- | --- |
| 成功率 | `check` 脚本通过的次数 / 3 |
| 改错和越界 | 改了不该改的文件、删了测试、留下垃圾文件，靠 git diff 自动判 |
| 轮数和工具调用数 | 从日志里统计 |
| token 和花费 | 各家自己报的用量，对不上的用代理统计 |
| 耗时 | 墙钟时间 |
| 人工评分（1–5 分） | 按 `rubric.md`：过程清不清楚、有没有乱问、结果好不好用 |
| 体验细节 | 只看 Atlas 和 ZCode、Claude Code 桌面端：界面上的进度显示、能不能看懂、操作顺不顺 |

## 5. 怎么跑

1. 写一个跑测脚本 `tests/t1/run.py`：按「参赛者 × 任务 × 次数」逐个执行。每次用干净的任务目录副本，结束后收集日志、diff、用量和 `check` 结果，存进 `tests/t1/results/<日期>/`。**结果目录不提交大文件**，只提交汇总表。
2. 用一个本地代理统一记录各家的模型请求，用来算 token。代理只转发，不改内容；API key 由各家自己带，代理不保存。
3. 一次只跑一个参赛者，避免互相抢资源。
4. 预算到了上限就停下来，先报告已有的结果。

## 6. 产出

1. `tasks/results/ATLAS-T1-HEAD-TO-HEAD.result.md`：
   - 总表：每个参赛者在每个指标上的平均分；
   - 逐任务表；
   - Atlas 赢的项、输的项，以及输的原因分析（附日志片段）；
   - 花费总计。
2. **T1F 补做任务书** `tasks/taskbooks/ATLAS-T1F-GAP-FIX.md`：
   - 每个输掉的项写成一节：输给谁、差在哪、对方怎么做的（看它的源码或文档）、Atlas 怎么改、改完怎么复测；
   - 格式照 C2 的任务书。
3. 在 CORE-PARITY 里，把输掉的项对应的行改回 △，写上「T1 输给 X」。

## 7. 然后

- 按 T1F 施工和验收：Sol 主控加独立验收，这时允许用真实模型复测**输掉的那几项**。
- 复测赢了或者打平以后，再进入外部功能阶段（`ATLAS-X-EXTERNAL-PHASE.md`）。
- T1 的跑测脚本和任务集留着，以后每次大改动以后可以重跑，当回归测试用。

## 验收清单

1. 20 个任务都能自动判定成败（11、19 这类可以「自动 + 人工」）。
2. 每个参赛者跑不了的原因都写清楚了。
3. 花费没有超过用户给的预算。
4. T1F 任务书里的每一项都有「对方怎么做的」的出处。
