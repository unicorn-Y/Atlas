# ATLAS-K1：上线前全面检查

> 前提：X2、X4 验收通过。
> 用户决定（2026-10-02）：X2、X4 做完后，全面检查一遍，确认没有别的问题，然后用户开始日常使用，之后按实际使用情况来优化（见 `docs/plan/USAGE-FEEDBACK.md`）。
> 本波取代 `ATLAS-O1-HERMES-PARITY.md`。O1 里的源码对照方法本波沿用；O1 的真实模型实测和浸泡环节，改由用户日常使用来代替。

## 本波目标

在用户开始每天使用之前，把能提前发现的问题都找出来并修好，让第一天用就顺手：
- 不崩、不丢数据；
- Hermes 有的能力在 Atlas 里都接通了；
- 出错时有看得懂的提示；
- 在笔记本（Atlas 自己的电脑）上常驻运行。

**不用真实模型。** 只有第 6 节的冒烟测试要用一次，开始前先问用户。

## 1. 在笔记本上装好、常驻

- 笔记本的开发环境重建：Python 3.14 的 venv，`pip install -e` 本地的 Hermes fork 和 `core`，装前端依赖。主机上的代码要先推送，笔记本再拉取。
- **开机自启**：后台常驻（Hub）随系统启动；断网、睡眠唤醒、模型服务出错后能自动恢复。
- **主机看笔记本**：主机先通过 SSH 隧道打开笔记本上 Atlas 的界面并派活。
- 写一份说明 `docs/user/laptop-host.md`：怎么启动、停止、更新到最新代码、看日志。

## 2. 源码对照：Hermes 的能力有没有都接通

照 O1 第 3 节的做法，但只列结论，不写长报告：

1. 把 Hermes 的这些东西逐项对到 Atlas：工具（`toolsets.py`）、斜杠命令（`hermes_cli/commands.py`）、桌面端调用的后端方法（`tui_gateway/methods_*.py`）、桌面端的功能（`apps/desktop/src`，`hermes-parity.test.ts`）、插件钩子。
2. 每一项标上：主体 / X2 / X4 / 以后的外部功能 / 不适用。
3. 「主体 / X2 / X4」这几类里，没接通的接上；Atlas 改过行为、又说不清好在哪的，改回 Hermes 的做法。

## 3. 用 Hermes 自己的测试检查 Atlas

Hermes 里相关的测试，在挂上 Atlas 的插件和工具层之后跑一遍。范围是文件、终端、压缩、委派、MCP、浏览器、电脑操作、技能市场。
- 原版能过、挂上 Atlas 就失败的，必须修。
- Windows 上原版本来就过不了的，沿用 C1R 的判断。

## 4. 日常路径走一遍（假模型，从 WebSocket 发起）

用假模型，把用户每天最常用的路径各走一遍，每条都要从界面能触发、结果对、提示看得懂：

1. 新建对话 → 选工作目录 → 改代码 → 看改动 → 撤回 → 重做
2. 长任务触发压缩后接着干
3. 中途插话、停止、排队
4. 计划模式出计划 → 执行
5. 子 Agent 并行 → 验收 → 汇总
6. 后台命令跑完后收到通知
7. 浏览器三步操作（X2）
8. 装一个技能并使用（X4）
9. 切换模型，切换权限档位
10. 关掉窗口后，定时任务照常跑
11. 模型服务返回 429 或 500，断网后恢复，看提示是否清楚
12. 重启 Atlas 后，对话、记录、设置都还在

## 5. 可靠性和体验检查

- **长时间运行**：用假模型连续跑 4 小时混合任务。看内存、句柄、孤儿进程（LSP、MCP、终端、子 Agent、浏览器）、日志大小。
- **错误提示**：故意制造常见错误，看提示是不是白话、有没有下一步建议、英文原文是不是只放在「详情」里。常见错误包括：密钥错误、模型名错误、网络断开、磁盘满、目录没有权限、MCP 启动失败、浏览器打不开。
- **界面检查**：无头 Edge 把主要页面在三套主题下各截一遍图，找出错位、溢出、空白、文案不通顺的地方。

## 6. 真实模型冒烟（开始前先问用户）

用用户日常用的那个模型，在笔记本上跑 3 个小任务：
1. 让它读一个目录并总结；
2. 改一个小 bug 并跑测试；
3. 用浏览器打开一个网页并提取内容。

只确认「真的能用」，不做对比。
