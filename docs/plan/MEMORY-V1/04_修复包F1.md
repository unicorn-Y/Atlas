# MEMORY-V1 修复包 F1：想得起来（语义召回）+ 中文一致 + 测试诚实 + 评测可信

版本 1.0，2026-10-08。编写：Claude（独立审查方）。施工：Codex，编排模式。
基线：Atlas `1abc5d49`、MemoryOS `164920a`（`memory-v1` 分支）。

## 0. 为什么要做（审查结论）

2026-10-08 独立审查（读代码 + 在主机复跑测试）结论：S0–S6 的实现是真的，没有发现造假；画像块修复有效。但 V1 还达不到门槛：30 条场景三次运行分别通过 21/17/19 条，门槛是 90%。根因已经查实：

1. **语义召回没有接到 V1 管线上**（任务书遗漏，责任在审查方）。
   - 只有旧管线 `service/candidate_ingest.py:419` 会调用 `semantic_recall.enqueue_memory_embedding`。V1 的 `service/unified/formation.py`（观察者写入的路径）和 `consolidation.py`（反思者写入的路径）都**从不入队 embedding**。
   - `semantic_recall.settings()` 的 `enabled` 默认读 `MEMORYOS_SEMANTIC_RECALL_ENABLED`，默认是 `"0"`，即关闭。
   - `retrieval._semantic_channel` 因此恒为 `NOT_WIRED`。召回只剩字面匹配：`_exact_channel` 只匹配 ASCII 词，`_fulltext_channel` 用中文两字组扫描。**换种说法就找不到**，例如问"我住哪"，记忆里存的是"用户常住杭州"，两字组没有重合。
2. **观察者输出语言不稳定**：`observer_prompt.py` 中的 Mastra 示例全是英文，temperature 为 0.3。中文对话有时被记成英文（一次运行中英文记忆占了 84 条，中文只有 2 条），中文提问就召回为空。这是三次评测结果波动的主因（`progress/profile_block_fix_2026-10-08.md` §3）。
3. **Atlas 集成测试没有如实报告**：总控只跑了默认的 `-m unit`，报 198 通过 / 2 失败。审查方用 `-o addopts=` 跑全集，结果是 **254 通过 / 10 失败**，而且有几个失败时有时无：
   `test_capture_lifecycle::test_chat_capture_user_and_assistant_observations`、`test_client_contract::test_service_down_raises_and_no_local_fallback_write`、`test_legacy_migration::test_legacy_export_import_roundtrip_idempotent_and_counts`、`test_multimodal_proxy::test_associate_via_proxy_returns_candidates_and_groups`、`test_release_composition::test_desktop_correction_is_visible_in_new_chat`、`test_repair_baseline::test_r00_b_0026_is_construction_not_foreign`、`test_repair_baseline::test_r00_b_dirty_counts_match_known_baseline`、`test_source_idempotency::test_flush_roundtrip_records_readable_status_counts_outbox_drained`、`test_windows_activity::test_capture_lifecycle_over_http`、`test_windows_activity::test_running_capture_passive_watermark_advances`
4. **评测只跑了一半**：LongMemEval 只做了抽题（`eval/longmemeval_subset.json`），**一题都没跑**；场景评测是单次运行，波动大到 17–21，结论不可信。
5. **流程问题**：上一棒总控最后 4 个提交只提交在本地、没有推送（已由审查方补推）。

## 1. 任务包（可以并行，文件所有权见各包）

### F1-A 语义召回接入 V1 管线（核心，最高优先级）
所有权：MemoryOS `service/unified/formation.py`、`service/unified/consolidation.py`、`service/semantic_recall.py`、`service/app.py`（只改 embedding worker 和配置的部分）、`service/unified/retrieval.py`（只改语义通道和融合权重的部分）。
1. formation 形成或更新一条记忆（有 key 或无 key）、consolidation 写出 MERGE / ROLLUP / PROFILE_UPDATE 的产物时，在**同一事务内**调用 `semantic_recall.enqueue_memory_embedding`（与 `candidate_ingest.py:419` 同样的语义）。被覆盖、被合并或删除的记忆，其 embedding 要按现有规则标为 stale，或交给 erasure 清理。HARD_ERASE 的 `14_embedding_queue` 层要如实覆盖（现在登记的是 `NOT_DEPLOYED`）。
2. 确保有后台 worker 消费 PENDING：调用 `semantic_recall.process_pending`，用本地 Qwen3-Embedding-0.6B。服务启动后在后台预热，**不阻塞 ack**。模型未就绪时，召回如实降级为字面通道，并在 `/v1/unified/status` 中显示 `semantic: WARMING/READY/ERROR` 和待处理数量。
3. V1 默认开启语义召回：Atlas 在自动拉起 MemoryOS 时（`service_lifecycle.py`）传入 `MEMORYOS_SEMANTIC_RECALL_ENABLED=1`；在 MemoryOS 侧也给出明确的配置项和默认值。所有权上，`service_lifecycle.py` 归本包。
4. 回填：给已有、没有 embedding 的 V1 记忆补建索引（隔离库中验证；生产库的回填放到 S7）。
5. 融合：`retrieval.py` 把语义分数并入现有的 Generative Agents 打分（relevance 取字面分数与语义分数的较大值，或者加权；权重写进配置）。语义命中也必须经过 `_memory_gate`（生命周期、as-of、项目过滤）。
- 完成判据（真实模型、真实服务、隔离库）：
  - 换说法召回：至少 10 对"记忆原话 → 不同说法的提问"，例如"用户常住杭州 → 我住哪""我对花生过敏 → 推荐菜谱时要注意什么"，召回命中率 ≥ 9/10；
  - 中英混合：英文记忆配中文提问能命中；
  - 删除之后语义通道召回为 0；
  - 1 万条记忆规模下，召回装配的本地开销 p95 ≤ 800ms（模型已预热，不含大模型调用）。

### F1-B 观察者与对话同语言
所有权：Atlas `core/atlas/memory/observer_prompt.py`、`observer.py`、`reflector.py`（只改提示词部分）。
1. 观察者和反思者的提示词加入硬规则："`text` / `value` 必须使用与原文相同的语言（中文对话写中文）；`key` 用英文点分 slug"。Mastra 的示例保留原有条目，另外为每类规则补一条中文示例（不删原条目，按 `02_上游搬运清单.md` 的要求）。
2. 输出校验：原文主要是中文、而 `text` 主要是英文时，判为不合格并重试一次。重试后仍不合格，就记录 `language_mismatch` 并保留原样，不丢弃，同时计数。
3. temperature 降到 0 或 0.1（如果配置允许）。
- 完成判据：用 10 段中文对话各跑 3 次，产出中文 `text` 的比例 ≥ 98%；附上统计。

### F1-C 测试诚实化
所有权：Atlas `core/tests/unified_memory/` 中上面列出的 10 个测试，以及它们依赖的 harness 片段（`tests/unified_memory/harness.py`）。
1. 每个失败逐个分类：① 真实产品缺陷 → 修产品代码（产品文件若属于其他包，就向那个包的负责人提需求）；② 依赖已删除的造假脚手架（例如 `fixture_desktop_correct_preference` 这类 fixture 工具）→ 改写成走真实服务和真实接口的测试，验证同一个用户效果；③ 测试的功能已冻结（多模态、被动采集）→ 用 `@pytest.mark.frozen_v1` 加原因明确下线，并在 `progress/KNOWN_FAILURES.md` 中登记；④ 时有时无（flaky）→ 查明原因（端口、临时目录、共享 fixture、并发）并修好，不得只是加重试。
2. `test_repair_baseline` 的两个用例比对的是 R00 时期的旧基准，基准已经过时：更新基准或下线，二选一，并写明理由。
3. **以后报告测试一律跑全集**：Atlas 用 `-o addopts= core/tests/unified_memory`，MemoryOS 用 `tests/unified_memory`。连续跑 3 次都全绿才算绿。
- 完成判据：Atlas 全集连续 3 次 0 失败（frozen_v1 计入 skip，并单独列出数量）；MemoryOS 保持全绿。

### F1-D 评测补全并变得可信
所有权：Atlas `scripts/memory_v1/`、`docs/plan/MEMORY-V1/eval/`。
1. 场景评测：F1-A、F1-B 合入后，30 条场景**跑 3 次，报告中位数**，同时报告每条场景的 3 次结果。达到稳定门槛的定义：E1–E4/E6 的中位数 ≥ 90%，反例 3 次都通过，E5/E7/E8 3 次都通过。
2. **LongMemEval 子集 120 题真正跑完**：走"观察者 → MemoryOS → 召回装配 → 回答"的完整链路，用官方评测脚本判分。报告总分、6 类分项、所用模型、token 和费用，并与 Mastra 94.87%、Hindsight 91.4%、Agent Zero 95.6% 对照。V1 门槛是 ≥ 80%。先跑 12 题（每类 2 题）的冒烟，并估算全量费用；全量费用估计超过 20 美元等值时，停下来请用户确认。
3. 评测报告必须写清楚：代码版本（两个仓库的 hash）、模型 id、运行次数、失败场景的根因分类。

### F1-E 总控流程纪律（总控自己执行）
1. 每整合一个任务包：提交**并且推送**两个仓库（用 `git@github.com:unicorn-Y/...` 的 SSH 地址），然后用 `git status -sb` 确认没有 ahead。推送前不得汇报"已完成"。
2. 每个任务包的验收都要附上全集测试结果（见 F1-C 第 3 条），不能只跑单元测试。
3. F1 全部完成后：更新 CURRENT.json（S3、S8 等相关步骤的状态和 note），写 `progress/F1.md` 汇总，然后**停下来向用户汇报**，等审查方审查。审查通过后才进入 S7（正式启用需要用户授权）。

## 2. 并行建议

可以立即同时开工：F1-A、F1-B、F1-C；F1-D 先做 LongMemEval 运行器和 12 题冒烟。F1-A、F1-B 合入后，F1-D 再跑完整的场景 ×3 和 LongMemEval 120 题。同一时刻保持 4–6 个子智能体在干活（GPT-6 Luna，推理强度 xhigh）；热文件只能有一个写者（见 `03_交接给Codex.md`）。

## 3. 红线

`00_任务书.md` 第 6 节全部适用。另外补充两条：
- 不得通过调低召回阈值、扩大 top-k、把历史全量塞进上下文等方式"刷"场景分数。修复必须作用在召回质量上，召回装配的长度限制（≤ 1500 token）不变；
