## 三、接入 `run_phases` 的硬障碍清单

在将评测完全切入 Atlas 核心聊天入口 `run_phases.execute_run` / `AgentOrchestrator.execute` 的过程中，定位到以下生产管线硬障碍：

1. **障碍 1：MemoryOS 冷启动与跨会话语义检索鸿沟**
   - **现象**：当第 1 回合捕获并存储“我在杭州工作，做跨境电商”后，第 2 回合输入“给我推荐几个适合我的周末活动”。MemoryOS 的 BM25 / 向量召回在无词面重叠时返回 0 条记录。
   - **根本原因**：测试环境下未常驻运行 `formation_worker`（`MEMORYOS_FORMATION_WORKER="0"`），画像尚未聚合为永久全局画像（Profile），冷启动语义泛化不足。
2. **障碍 2：`run_phases` 对外部 `SessionDB` 预写入的紧耦合**
   - **现象**：直接调用 `execute_run` 时，`_capture_run_user_message` 与 `_capture_run_assistant_message` 静默返回，不进行消息捕获。
   - **根本原因**：`run_phases` 设计假设消息在进入 `execute_run` 之前已由 WebSocket 路由层（`run_drive.py`）写入了 `DATA_ROOT / "engine"` SQLite 数据库；脱离完整服务器驱动时，由于 SessionDB 中尚无持久化记录，自动捕获机制找不到稳定的 `message_uid` 而提前退出。
3. **障碍 3：Hermes 运行时全量工具探测与多轮推理超时开销**
   - **现象**：通过 `AgentOrchestrator.execute` 全量启动 `HermesRuntime` 时，每次对话需探测并加载全部 72 个本地/MCP 工具。
   - **根本原因**：对于纯记忆对话场景，模型在系统提示词无直接记忆时会倾向于发起 `session_search` 或文件搜索工具调用。在沙箱禁用或测试受限环境下，引发多轮错误重试，导致单轮耗时超过 60-90 秒甚至触发超时。
4. **障碍 4：时区格式严格校验契约限制**
   - **现象**：`01_验收场景.md` 中给出的原始时间戳多为 naive 格式（如 `"2026-10-01 10:00:00"`），直接送入 MemoryOS `POST /v1/unified/observe` 会触发 HTTP 422 `ContractViolation`（“不接受 naive 时间假装绝对时间”）。
   - **对策**：输入端必须规范化为带时区偏移的 ISO8601 字符串（如 `+08:00`）。

### 5.3 真实失败原因深度分析
真实重跑揭示了当前产品真实存在的若干短板（而非掩盖）：
1. **反例克制（如场景 4 / 5）**：真实模型在面对模糊提问（如“你觉得我该不该搬去上海？”）时，观察者容易过度提取潜在意图；在回答“我住哪”时，模型存在一定的地点幻觉。
2. **观察者单日预算熔断（Token Budget Exhaustion）**：
   在连续运行到第 6 场景后，`MemoryObserver` 的单日预算（50,000 Token）耗尽，触发 `memory_observer.budget_deferred`，后续场景的观察者提取被系统安全熔断推迟，导致后续轮次记忆未能及时生成。
3. **格式严格约束（如场景 11 Markdown 表格）**：
   模型在第 2 轮回答时记住了用户偏好并引用了 `[m:ref_11_1]`，但选择先向用户追问表格细节而非直接给出周报表格，导致规则检测器未匹配到表格语法。
