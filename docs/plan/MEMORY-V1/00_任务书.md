# Atlas 记忆 V1 任务书：能用、记得住、不会乱

版本 1.0，2026-10-07。编写：Claude（独立审查方）。施工：Codex。
本文件在 Atlas 与 MemoryOS 两个仓库的 `docs/plan/MEMORY-V1/` 中各有一份，内容相同。

> 本任务书**取代** `docs/plan/UNIFIED-MEMORY/`（原 UM00–UM13）和《达标修复施工包》（R00–R27）的施工顺序。这两份旧计划保留作参考资料，其中的目标并未作废，只是延后到 V2 及以后。原则仍然有效：真实效果优先、不准造假、出处可追溯、删除不会复活。

## 0. 一句话目标

**让用户日常使用的 Windows Atlas 真的记得用户：换会话、重启、隔天都不用重新介绍；能自然想起相关的人和事；越用越清楚而不是越乱；记错了能改，要删就真删。**

V1 之后用户开始天天使用，边用边修。图片/声音/屏幕（V2）、自主学习与经验迁移（V3）、情绪权重（V4）不在本期。

## 1. 用户能感受到的 V1 效果（验收以这 8 条为准）

| # | 效果 | 反例（必须不发生） |
|---|---|---|
| E1 | 说过的个人信息、偏好、项目约束，新会话 / 重启 / 隔天后仍然知道，不用再说 | 换个会话就忘；把用户的提问当成用户的陈述 |
| E2 | 自然提到"上次那个人""前几天定的事"时能想起来；有多个候选时会追问 | 混淆两个同名的人；编造没发生过的事 |
| E3 | 记忆在相关时自然生效，例如回答格式、项目约束、偏好 | 问无关问题时硬塞用户私事 |
| E4 | 区分当前状态和历史："后来改成周五"以后，回答以周五为准，但问起时记得原来是周三 | 新信息覆盖得不留历史；旧信息晚到时反而覆盖新信息 |
| E5 | 用了几周之后记忆仍然清晰：重复的已合并，过时的已标注，不常用的排在后面，但被问到时仍然找得到 | 召回结果里同一件事出现 10 次；老记忆永久消失 |
| E6 | 能回答"你是怎么知道的"：指出是哪次对话、哪句话 | 给不出出处，或者给出假出处 |
| E7 | 用户在记忆页面能看到记了什么，并且能改、能删、能暂停记录；改或删之后聊天立即体现 | 删了之后又冒出来；改了但聊天还用旧的 |
| E8 | 说"下次打开 X 时提醒我""明天提醒我"会真的提醒；中断的任务回来能接着做 | 提醒没有触发、触发两次，或者取消了还提醒 |

## 2. 现状（2026-10-07 实查，不是推测）

**可以保留的骨架**（MemoryOS 分支 `unified-memory/waves`）：
- `/v1/unified/*` 统一 API：observe / recall / records / evidence / profile / entities / corrections / timeline / intents / focus / export / maintenance / status
- `service/unified/formation.py`：同一个键的冲突裁决、新旧覆盖（SUPERSEDE）、迟到的旧证据不覆盖新证据、事件形成。**但它只接收已经带 `content.key/value` 的结构化观察**
- `temporal.py`（有效区间、as-of 查询）、`identity.py`（实体与别名，目前用字符串相似度代替 embedding）
- 检索 `retrieval.py`：精确 / 全文 / 时间 / 语义（sqlite-vec + 本地 Qwen3-Embedding-0.6B）/ 焦点五路
- 删除：`erasure.py` 和 `erasure_restore.py`，覆盖 HARD_ERASE、防复活屏障、备份恢复
- Atlas：`unified_client.py`、`unified_facade.py`、`capture.py` + `outbox.py`（聊天和工具经历的可靠采集）、`/api/unified-memory/*` 代理、`focus_flow.py` / `reconcile.py`（中断接续）、`intent_bridge.py`（意图到 Automation）、MemoryPage 及 7 个组件

**导致"用起来没记忆"的真实断点**（V1 必须修）：
1. **统一记忆在生产环境是关闭的**：`memory.unified.enabled` 默认是 false，`D:\Atlas\data\user-settings.json` 里也没有开启。MemoryOS 服务没有运行，8099 端口没有监听；Atlas 也不会自动拉起它。
2. **聊天读到的是旧的本地库**：`run_phases._phase_context` 调用 `MemoryStore.get_agent_context_with_trace` → `get_active_context` → `list_facts()`，读的是 Atlas 本地 `facts` 表，并且只做关键词计分。写入已经委托给 MemoryOS，读取还停在旧库，所以新写进去的记忆聊天读不到。
3. **没有模型参与记忆形成**：`MemoryStore.extract_memories` 只认 `remember: key = value` 这一行格式；`extract_conversation_candidates` 是正则模板。普通聊天几乎形成不了记忆。生产库里有 32,905 条 evidence_events，只形成了 67 条 memories。
4. **没有整理与淡忘**：`consolidation.py` 没有注入模型，只走确定性的兜底生成器；检索不按时间远近和使用频率排序。
5. **测试脚手架造假尚未清干净**：Atlas harness 里的 `_synthesize_scripted_response` 会替产品作答（修复包 R02 未完成）。

**V1 冻结不动**（代码保留，在运行时用配置开关关闭，不删除）：多模态媒体理解（`multimodal.py`、`media.py` 的理解部分）、被动屏幕采集（`windows_sources.py` 的被动部分）、技能演化（`skill_evolution.py`）、定向学习（`targeted_learning.py`）、预测（`prediction.py`）、条件效用（`utility.py`）、策略更新（`strategy_updates.py`）、`learning_gate.py`、`experience_distiller.py`、A-mem 关联演化、HippoRAG 图检索、自测（`self_probe.py`）。

## 3. 架构决定（不得改）

```
用户 ⇄ Atlas 聊天 (run_phases)
          │  ① 采集：capture.py → outbox → POST /v1/unified/observe（原文，已有）
          │  ② 观察者 Observer（新，Atlas 侧，异步，不阻塞回答）
          │       读本轮原文 → 模型（ModelRouter）→ 结构化观察 → POST /v1/unified/observe
          │  ③ 召回 Recall（改，Atlas 侧装配）
          │       每轮：画像块(稳定) + POST /v1/unified/recall 相关记忆(带出处)
          │  ④ 反思者 Reflector（新，Atlas 侧，空闲/每日）
          │       GET 记录 → 模型提出整理操作 → POST /v1/unified/consolidation:apply
          ▼
MemoryOS（唯一记忆权威）：存储 / 冲突裁决 / 时间版本 / 检索与淡忘排序 / 纠正 / 删除
```

1. **用到模型的工作都放在 Atlas 侧**，统一经过 `ModelRouter.complete_for(model_id, purpose, ...)`（参照 `core/atlas/engine/branch_summaries.py` 的用法）。新增 purpose `memory_observe` 和 `memory_reflect`；模型由用户设置 `memory_model` 指定，未设置时退回 `compression_model`，再退回当前模型。**MemoryOS 不新增任何模型配置，也不直接调用大模型。** embedding 仍使用 MemoryOS 自带的本地 Qwen3-Embedding。
2. **MemoryOS 是唯一权威**。模型只负责"提议"，由 MemoryOS 裁决：冲突、覆盖、合并是否成立、出处是否存在。模型的输出永远是 `DERIVED`，并且必须带 `derived_from`（原文 source_event_id）。
3. **原文永不自动删除。"淡忘"是排序上的降权，不是删除。** 真正的删除只走用户发起的 HARD_ERASE。
4. **两个 Python 环境之间只通过 HTTP 通信**，不得跨环境直接 import。
5. **不新增第二套事实库、调度器或配置库。** 提醒继续走现有的 Automation（`intent_bridge.py`）。

## 5. 施工分步（S0 → S8，严格按顺序；每步结束停下等审查）

通用要求（每一步都适用）：
- 分支：两个仓库都从当前 `unified-memory/waves` 拉出新分支 `memory-v1`。每步至少提交一次，提交信息以 `feat(memory-v1): S<n> ...` 开头。只推送 `memory-v1`，不合并 main。
- 测试数据：必须使用隔离的数据根（`ATLAS_DATA_DIR`、`MEMORYOS_DATA_ROOT`、`MEMORYOS_DB_PATH`）。**不得用生产库 `D:\MemoryOSData` 和 `D:\Atlas\data` 跑测试**；只有 S7 的回填在用户授权后才可以碰生产库。
- 每步交付：代码、单元测试、该步的「真实冒烟」（用真实模型、真实服务，条数见各步）、`docs/plan/MEMORY-V1/progress/S<n>.md`（做了什么、怎么验证的、原始输出、已知问题），并更新 `docs/plan/MEMORY-V1/CURRENT.json`。
- 状态只能写 `IN_PROGRESS` / `DONE_PENDING_REVIEW` / `BLOCKED`。**`ACCEPTED` 只能由审查方写。**
- 已有测试在本步之后不得变少，也不得被改成 skip 或 xfail。新出现的失败要么修好，要么在 progress 里如实列出。
- 真实冒烟按用户"实测集中到最后"的要求控制配额：S1–S6 每步 5–10 条，大规模评测放在 S8。

### S0 清场与开关（小）
1. 完成修复包 R02 的核心部分：删除 Atlas 测试 harness 中的 `_synthesize_scripted_response` 和一切按关键词返回固定答案的逻辑。harness 只能转发给真实的服务或模型；用假模型的测试必须显式标注 `fake_provider`，且不计入效果。
2. 新增配置开关 `memory.v1.frozen_features`（默认把第 2 节列出的冻结模块全部关闭），使冻结模块不进入聊天和后台的运行路径；它们的单元测试照常保留。
3. 修复或如实登记已知的测试失败：MemoryOS 的 `test_legacy_import` 2 项（在干净 HEAD 上也失败）；Atlas 的 `test_bootstrap::test_chat_roundtrip`（该用假模型，结果请求漏到了真实供应商：查明环境变量泄漏的原因并修复）。
- 完成判据：两个仓库测试全绿，或剩余失败附有已证明的、与本次无关的原因；`grep -rn "_synthesize_scripted_response\|fake-model" core scripts` 不再命中业务或验收路径。

### S1 读写打通：聊天只读统一记忆（核心）
1. **Atlas 自动拉起 MemoryOS**：Atlas 后端启动时（`server.py` lifespan 或 `deferred_startup.py`），若 `memory.unified.enabled=true` 且 8099 无服务，就用 MemoryOS 的 venv 启动 `service/app.py`（路径由配置 `memory.unified.service_dir` 指定，默认 `D:\MemoryOS`）。加入健康检查；Atlas 退出时一并关闭。MemoryOS 不可用时，聊天照常进行，并在状态栏显示"记忆离线"（参照现有 15 秒熔断语义），不得阻塞回答。
2. **读路径切换**：`memory.unified.enabled=true` 时，`run_phases._phase_context` 不再调用 `get_agent_context_with_trace` / `get_active_context` / `list_facts` 读本地 `facts` 表，改为调用 S3 的召回装配器（S1 先用 `POST /v1/unified/recall` 直接返回结果的最小版本，S3 再增强）。`MemoryStore` 中所有面向用户的事实读方法，在开启时都委托到 `/v1/unified/records` 或 `/recall`；本地 `facts` 表变为只读的旧数据。
3. **旧数据迁移**：用已有的 `scripts/unified_memory/import_legacy.py`，把 Atlas 本地 facts 和候选数据导入隔离库验证一遍（记录数、内容哈希、出处），生成 dry-run 报告。正式导入生产放到 S7。
4. 打开开关的方式：只改 `user-settings.json` 的 `memory.unified.enabled`，以及新增的 `service_dir`。改动前先备份原文件。**生产开关在 S7 经用户同意后才打开**；S1 只在隔离数据根中验证。
- 真实冒烟（5 条）：在隔离环境用真实模型，通过 `remember: 城市 = 杭州` 这类已有的显式记忆写入 → 新开会话 → 问"我住哪" → 回答引用 MemoryOS 的记录；关闭 MemoryOS 后聊天不卡死，状态显示离线；重启 Atlas 后 MemoryOS 被自动拉起。
- 完成判据：开关打开时，`run_phases` 的上下文中不出现任何来自本地 facts 表的记忆（写测试断言：在本地表塞入一条独有事实，它不得出现在上下文里）。

### S2 观察者 Observer：普通聊天自动形成记忆（核心）
1. 新文件 `core/atlas/memory/observer.py`：
   - 触发：每轮回答完成后异步执行（不阻塞流式输出）；同一会话累积到阈值（参照 Mastra `thresholds.ts`，按 token 计）或会话结束时批量处理。
   - 输入：本批的原文消息（用户、助手、工具结果摘要），连同它们在 capture 中的 `source_event_id`、时间和时区。
   - 提示词：搬运 Mastra `OBSERVER_EXTRACTION_INSTRUCTIONS` 与输出格式（优先级 🔴🟡🟢、"陈述 vs 提问"区分、日期写在末尾、拆分规则、状态变化要明说），并扩展为**结构化 JSON 输出**，每条包含：
     `text`（自然语言要点）、`priority`（HIGH/MEDIUM/LOW）、`facet`（取 contracts.FACETS 中的 FACT/PREFERENCE/STATE/HABIT/RELATION/EPISODE/GOAL/COMMITMENT/INTENT/KNOWLEDGE）、`key`（稳定的属性键，如 `user.home_city`、`project.atlas.test_policy`；事件和一次性经历可以没有 key）、`value`、`entities`（涉及的人、项目）、`valid_from` / `valid_to`（能确定时才填）、`is_change`（是否为"后来改了"）、`evidence`（对应的 source_event_id 列表，至少一条）、`speaker`（USER/ATLAS/TOOL/THIRD_PARTY）。
   - 校验：JSON schema 校验；`evidence` 必须是本批真实存在的 id，否则丢弃该条并计数；用户的提问不得变成"用户陈述"（例如"我该不该搬去上海？"不是"用户要搬去上海"）；网页、文件、工具里的内容一律是 THIRD_PARTY，不得变成用户的事实。
   - 输出：转成 `ObservationBatch` 提交 `POST /v1/unified/observe`，其中 `source_kind=DERIVED`、`derived_from=evidence`、`epistemic_kind` 按 speaker 映射（USER→USER_ASSERTED，TOOL→OBSERVED，THIRD_PARTY→THIRD_PARTY_ASSERTED，其余→INFERRED）。
2. **MemoryOS `formation.py` 补一条"无 key 记忆"路径**：`content.key` 为空但 `text` 非空时，形成 `facet=EPISODE/KNOWLEDGE/...` 的记忆记录（不参与按 key 的冲突裁决，按归一化正文去重，保留 derived_from），这样经历类要点也能进入记忆。带 key 的观察继续走现有的冲突、覆盖逻辑。
3. 意图：`facet=INTENT/COMMITMENT` 且含提醒条件的，交给 `intent_bridge.py` 建立提醒（S6 再验证端到端）。
4. 成本护栏：每批的 token 上限、每日 Observer 预算（配置 `memory.v1.observer_daily_token_budget`）。超出预算时排队顺延，**不丢弃原文**（原文已经由 capture 入库）。
- 真实冒烟（10 条中文对话，用真实模型）：陈述与提问混在一起、偏好、项目约束、状态变化（"本来周三，改周五"）、提到两个同名的人、粘贴一段网页内容（不得成为用户事实）。逐条列出形成的记录、出处和误差。
- 完成判据：上面 10 条里，用户陈述被正确形成 ≥ 9 条；提问或网页内容被误当成用户事实的 = 0；每条记忆都能通过 `GET /v1/unified/evidence/{ref}` 打开原句。

### S3 召回 Recall：每轮自动带上相关记忆（核心）
1. 新文件 `core/atlas/memory/recall_context.py`，供 `run_phases._phase_context` 调用，输出两块：
   - **画像块（稳定）**：由 S4 的反思者维护的"我对用户的了解"，即 `facet=SUMMARY`、scope=PROFILE 的记录，≤ 600 token。放在系统提示词靠前、稳定的位置，以便吃到 prompt cache（Mastra 的做法）。S4 完成前用 `GET /v1/unified/profile` 的现有输出代替。
   - **相关记忆块（每轮）**：`POST /v1/unified/recall`（query = 当前用户消息加最近 1–2 轮的摘要），取 top-k（默认 8，总长 ≤ 1500 token）。每条带 `[m:<短 ref>]` 标记、日期，以及"当前 / 历史"标注。
2. **意图闸门**（参考 Agent Zero 的 intent gate）：替换 `context.is_personal_memory_relevant` 的正则判断，改为"embedding 相似度阈值 + 轻量规则"，**不在每轮额外调用大模型**。纯技术问题、与用户无关的问题只给画像块，不给私事。阈值写入配置，在 S8 用验收集标定。
3. **出处**：在系统提示词里说明 `[m:…]` 的含义；用户问"你怎么知道的"时，模型应引用 ref，Atlas 前端把 ref 渲染成可点击的出处（打开 EvidencePanel）。**只允许引用本轮真正装配进上下文的 ref**；输出中出现不存在的 ref 时，前端显示为"未验证"。
4. 冲突与歧义：recall 返回 CONFLICTED 或多个同名实体候选时，在记忆块中明确标出"有冲突 / 有多个候选"，提示模型先问清楚再回答。
- 真实冒烟（10 条）：E1、E2、E3、E4、E6 各 2 条，用真实模型在 Atlas 真实聊天入口跑（脚本调用 `/api` 或 WS 均可，但必须经过真实的 `run_phases`）。
- 完成判据：上下文装配有日志（每轮装配了哪些 ref、为什么装配、闸门判定结果），可以从日志复现。

### S4 反思者 Reflector 与淡忘排序：越用越清楚（核心）
1. 新文件 `core/atlas/memory/reflector.py`：
   - 触发：每天一次，在空闲时段执行（复用现有 Automation/调度，不新建调度器）；另外，当某主体未整理的新记忆超过阈值时也触发。
   - 搬运 Mastra `reflector-agent.ts` 的指令：合并相关条目、浓缩模式、保留关键细节和日期、去掉冗余。改造成**输出操作列表**而不是整段重写：
     - `MERGE {refs:[...], into_text, keep_ref}`：同一件事的多条合并为一条，被合并的标为 SUPERSEDED_BY_MERGE，并保留指回原条目的链接
     - `SUPERSEDE {old_ref, new_ref, reason}`：明确的新旧替代关系（formation 没有自动判出的）
     - `ROLLUP_DAY {date, refs, text}` / `ROLLUP_WEEK`：生成每日 / 每周概括（facet=SUMMARY，derived_from 指向原记录）
     - `PROFILE_UPDATE {text, refs}`：更新"我对用户的了解"画像（facet=SUMMARY、scope=PROFILE，≤ 600 token，每句话可追溯到 refs）
     - `IMPORTANCE {ref, level}`：调整重要性
   - 禁止的操作：删除、修改原文、引用不存在的 ref、凭空写出没有出处的新事实。
2. **MemoryOS 新增 `POST /v1/unified/consolidation:apply`**（在 `consolidation.py` 和 `api.py` 中实现）：逐条校验操作（ref 存在且属于同一主体、未被删除、操作类型合法、derived_from 完整），在事务里执行并写修订记录（revision），返回每条操作被接受或拒绝及原因。被拒绝的操作不得部分生效。删除屏障同样适用：已 HARD_ERASE 的内容不得因概括而复活（概括的 derived_from 中若有被删条目，就把该概括标为 stale 并在下次重算）。
3. **淡忘排序**（在 `retrieval.py` 的最终排序中实现，出处注明 Generative Agents）：
   `score = w_rel·relevance + w_imp·importance + w_rec·recency_decay + w_use·reinforcement`
   - recency_decay = 0.5^(距今天数 / 半衰期)。半衰期按 facet 设置：STATE 14 天，EPISODE 60 天，FACT/PREFERENCE/RELATION/COMMITMENT 不衰减（只受被覆盖、被合并影响）。
   - reinforcement 由已有的 read receipt 或应用回执统计得出：被召回且真正被用到的次数，按对数增长，设上限。
   - HIGH 重要性设下限，永远不会被排到看不见。
   - **衰减只影响排序，不影响能否被找到**：精确查询或时间查询仍然能找到老记忆（写测试：一条 200 天前的 EPISODE，用精确问法必须能召回）。
   - 所有权重和半衰期写入配置，并在 S8 用评测集标定。
- 真实冒烟（5 条）：构造 2 周的对话轨迹（每天 3–5 段，用真实模型跑 Observer，时间可以通过 occurred_at 模拟，但内容必须由真实模型形成），跑反思者 → 检查合并、日 / 周概括、画像是否正确、可追溯；同一件事说了 5 次只召回 1 条（附出处链）；问起 2 周前的细节仍然找得到。
- 完成判据：被拒绝的操作有清楚的原因；对同一份输入重复运行反思者结果幂等（不会越合并越少直到丢信息）。
