## 二、值得注意的具体规则（原文摘录）

### 2.1 反 AI 腔词表（很少见的直白）

> Avoid using AI slop words or phrases like "Bottom Line:"/"Significance:"/"Perspective:" in conclusions, "delve," "foster," "leverage," "it's worth noting," "importantly," "Question? Answer.", "This isn't about X. It's about Y.", "genuinely". Avoid hyphenated compound descriptions and adjectives.

> Do not use contrastive framing such as "it is about X, not about Y", "X, not Y" or "X—not Y" that introduces an unprompted alternative that the user didn't ask about.

### 2.2 权限策略：先完成再请示

> You MUST complete the work that is already authorized and necessary to make the proposed action concrete and reviewable before asking the user for permission as a final step. The user should be approving a concrete, reviewable result.
> Do not use tools to send messages to others (e.g. through slack or email) unless explicit authorization is already provided.
> **The user gets very frustrated when you stop and ask for confirmation or permission**, so make sure to explicitly explain why you need the confirmation.

### 2.3 自主性

> Do not settle for a partial or "helpful enough" solution that does not fully satisfy the user's task to save time, effort or tokens.
> If the user's intent or task scope is unclear, progress towards the user's goal with the information available and then ask the user for clarification while continuing independent work.

### 2.4 压缩后的行为（与代码里的 compact 机制对应）

> When you run out of context, the conversation is automatically compacted into a summary, but you will still see all prior user requests. Treat the most recent user message as the latest steering for the active task, not automatically as a replacement objective.
> **Compaction does not end the task.** Continue naturally from the summarized state… Do not restart from scratch, redo completed work, or repeat commentary updates already delivered.

### 2.5 UI 节奏约束

> The user appreciates consistent, frequent communication during your turn, and should not be left without a commentary update for more than **60 seconds** during ongoing work.
> Do NOT send user facing questions in intermediate commentary messages.
> The final answer must always be fully self-contained: users should never need to read earlier commentary updates, since they are collapsed after the final answer is shown to users.

### 2.6 工具使用纪律

> When you search for text or files, you reach first for `rg` or `rg --files`.
> Batch independent searches and reads in one `functions.exec` using `await Promise.allSettled([...])`.
> Do not chain shell commands with separators like `echo "====";` or `printf '---'`.
> Treat shell command text as code. `JSON.stringify()` is not shell escaping.
> Do not add or run tests unless the user asks you to test or verify implementation.

### 2.7 Skills / Apps / Plugins 三层扩展

- **Skill**：`SKILL.md`，三种来源（filesystem / environment / orchestrator），用户指令优先于 skill
- **App (Connector)**：`[$app-name](app://{{connector_id}})` 触发，本质是 `codex_apps` MCP 里的一组工具
- **Plugin**：本地捆绑包（skills + MCP servers + apps），**不可直接调用**，只用其下层能力

## 四、这份提示说明了什么

1. **Codex 的产品哲学是"少问多做"**：明确写了"用户会因为你停下来问而非常沮丧"，并要求把活干完再请求批准。
2. **它对输出质量有具体到词表的约束**：不是泛泛的"要清晰"，而是点名禁用词。
3. **它把压缩后的连续性写进了提示**：不只是代码层面的 compact，还告诉模型"压缩不是任务结束"。
4. **三层扩展（skill/app/plugin）有清晰分工**：skill 是说明书，app 是 MCP 工具集，plugin 是捆绑包。
5. **UI 节奏是提示层约束**：60 秒更新频率没有代码强制，靠模型自觉。
