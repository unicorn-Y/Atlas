# Embedded message, task, and stream protocol schemas

## Exact artifact and extraction boundary

The schemas below are present as executable schema-construction source in the embedded Bun payload of `package/claude.exe` from the exact Windows package. Executable SHA-256: `3ab075f78998efef8b87f491c2e4a39c309dddf44e51d0103eba4f3713d2a0ae`; package archive SHA-256: `cd077f50f24f5155c28800a3658a58c89b5d1ccae2f95a2e096a16ab250a544d`.

The byte spans below contain source fragments shaped like `f(()=>u({type:C(...), ...}))`, including schema validators and field descriptions. They are application-bundled wire-schema definitions, stronger than isolated string hits. They establish declared message structure in this build; they do not establish which producers emit each field, actual serialization at a running session, event order, server-side interpretation, or a stable public promise. Descriptions explicitly distinguish optional/older-producer behavior and some hosted/bridge paths.

## Agent/event interpretation grounded in the schema

1. Parent-child provenance is a first-class nullable `parent_tool_use_id` on both user and assistant frames and on streaming/progress envelopes; it is not necessarily inferable from text nesting.
2. A task is not represented by one boolean. The schema carries stable `task_id`, per-run `run_id`, spawning `tool_use_id`, `parent_task_id`, depth, task type, background/awaited state, and separately `task_started`, patch updates, terminal notification and a replace-all live-background snapshot.
3. Backgrounded tool completion can be split: the originating tool result is placeholder text, and the real result arrives through `task_notification` with an explicit `tool_use_id` join. A consumer that treats every first result as terminal loses the actual child report.
4. Tool output and permission/execution status are distinct. Structured `tool_use_result` is not the same as model-visible `tool_result`; `non_execution_kind` is the marker for an error that did not run, whereas metadata presence alone is insufficient.
5. Restart continuation has protocol-level fields (`resume_reason`, user-message UUID binding and interrupted turn data) in addition to the state-selection implementation described in `12-native-supervisor-source.md`. No actual restart event was generated in this investigation.

## Atlas comparison at pinned main

Baseline `main@aa6196f550098cc46081dc6db2c376cb87ddffa5`:

- `core/atlas/api/run_drive.py:2132+` constructs Atlas runtime event envelopes; `:1951-2033` normalizes the external ACP update path into a narrow Atlas event family.
- `core/atlas/runtime/external_agents.py:60-98` recognizes a limited set of `agent_message_chunk`, `tool_call`/`tool_call_update` and error updates. Unknown update types are not a generic pass-through contract.
- `frontend/src/renderer/services/runtimeEvents.ts:25-84` validates/project events into the bounded UI event buffer. Existing source does not define the Claude fields above (`parent_tool_use_id`, `task_id/run_id` split, task snapshots, structured tool result metadata and result accounting phases) as the native Atlas event contract.

Assessment: Atlas has working orchestration/progress projections, but **the inspected external-event adapter is a partial mapping**, not a faithful implementation of the bundled Claude event/task schema. This source comparison does not prove an ACP peer emits all these native event variants, nor does it require Atlas to mirror a Claude-specific interface. No live Claude or Atlas event stream was captured.
