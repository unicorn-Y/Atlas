# 最小实证计划：先让方案可比较，不扩大无谓开发

本文件是**研究的建议施工顺序和验证协议**，不是已经派工或已运行结果。目标是不再反复造轮子，强调少量高价值反例而不是用几千条无效 pytest 凑覆盖率。

## A. 先整理分支和证据（暂不替换架构）

- 保留 `memory-v1`, `memory-w2-api`, `memory-w2-ui` 的固定 SHA，列 3-way diff；核对后端 API 与 UI 字段、合并冲突、哪些专项/端到端测试已经 PASS / FAILED。
- 精确追溯主机使用哪一分支、哪个 `data/memory`、哪个 `engine/state.db`，并只读备份测试材料；不要直接在真实数据上重算/清空。
- 重点修复 W2 Dream 日常运行潜在跳过未成熟 group、来源引用靠 timestamp 模糊定位、跨项目 trigger 混用这三个高风险问题。
- 追查 `skill_sleep.py` 计划调度、真实成功/失败反馈以及写入的 SKILL 是否被加载；先记录客观事实，再决定可否替换。

## B. 只对会影响最终架构的核心设计做实验

| 实验编号 | 对照 | 关键问题 | 预期输出 |
|---|---|---|---|
| E01 | W2 dream vs ReMe checkpoint | 3 天增量、昨日待分类、重启重试会不会丢/重写记忆 | 每个证据 ID 处理状态、派生数据可重算 |
| E02 | W2 weighted+MMR vs Hindsight RRF | 中文同义词 vs 错误码/路径 vs 跨时间来源，谁命中正确证据 | 每题 hits/误召/消耗/延迟 |
| E03 | W2 直接摘要 vs AMA-Agent sufficiency+邻域 | “当初为何作这个决定”是否从原始轨迹拿足证据 | 充分/不充分识别准确率、扩展读次数 |
| E04 | W2 project trigger vs 显式 project ID | 相同 `status` 或文件名跨两个仓库会不会错误合并 | 误合并率和漏合并率 |
| E05 | W2 fact vs Graphiti 双时间 | 软件配置 A→B→C，问不同日期分别什么版本 | 时间回答/更正、证据命中 |
| E06 | 实现前召回 vs MemOS failure/skill触发 | 两次相似报错能否主动想起，但不误用不同根因旧招 | 后续任务减少失败步骤与误触发 |
| E07 | 当前 skill_sleep vs 入口 Eligibility + SkillOpt | 自动学到的 Skill 是否在留出任务改善，不回归 | replay、adopt、rollback、实际调用统计 |
| E08 | Scope/删除传播 | 被撤回的内容是否经摘要、旧设备、向量检索复活 | 指定源的所有活跃视图中无禁用数据 |

**对照标准**：相同原始日志、相同模型、温度、上下文 token 预算、硬件/存储环境和成功定义。作者公开 benchmark 和 GitHub 星数不当“本机胜出证据”。既比较检索命中，也比较真实后续任务正确率和纠错/拒答。

## C. 高价值样例（JSONL 在 `tests/atlas_memory_research_cases.jsonl`）

- 同一日两个不同项目出现完全一样的错误码。
- Day1/Day2 梦境运行但两天未成熟，Day3 第三天累积，必须包含所有三天证据。
- 故意伪造一个用户没有说过的个人爱好，拒绝承认为事实。
- 两条消息同一秒，source ref 必须指向精确 message_id。
- 某命令 exit=0 但任务验收失败，不能 Skill 晋升。
- 外部 Agent 猜测与用户明确决定矛盾时，模型猜测不覆盖用户事实。
- 撤回事件后从每日摘要与旧电脑重连不能复活。
- 需要相邻 3 个工具动作才能解释因果；只返回第 2 个相似片段不够。
- 视觉/语音暂缓：只用**合成多模态 envelope** 跑 schema 验证，不用真的截图/录音。

## D. 何时允许换数据库/运行时

不先定 SQLite 还是 Postgres。以 1 万、10 万事件（包括不同来源/轨迹）为小/中型样本，在同机比较初始化、更新、读路径 p50/p95、索引占用、离线/重启恢复、设备同步并发、维护复杂度；原有数据迁移做 replay 和影子双读。若轻量方案在目标情景足够好，优先维护成本小；若复杂查询和并发明显获益，再用 Postgres 或更专门的索引结构。没有证据就不批准整个数据库层重写。

## E. 从研究到施工的最小切片（顺序可因实测调整）

**S0 整合**：W2 已实现功能合并/复核，拿到可复现基线；不加新库。

**S1 事件基础**：稳定事件 IDs、schema、来源、可追溯 raw ref；包括 Atlas chat/tool 和外部 Agent 的输入适配。此处只处理文本与工具，不写多模态采集。

**S2 情景与 Claim Gateway**：真正 episode、双时间、纠错、更正、过期、scope、删除传播；和 W2 现有页面做兼容输出，不立即再造 UI。

**S3 执行中主动召回**：五入口策略、回忆详情/邻域、与 W2 hybrid/Hindsight 的实验胜出算法整合；只保留一个检索融合主实现。

**S4 巩固/反思**：逐证据 checkpoint、跨天处理、失败重试、防自回流、反例纠正；考虑保留 ReMe schema。

**S5 经验→Skill 闭环**：ReasoningBank/MemOS candidate、Atlas SkillOpt replay/gate、任务使用反馈与回滚。

**S6 多设备共享**：外部 Agent 写权限、离线同步和数据边界，以工作空间/项目先行。**视觉/语音/手机感知端 S7 以后再实施**，本轮只制定其契约和验收方案。

## F. 必须拒绝的施工单

- “把 ReMe、Graphiti、MIRIX、Hindsight、MemOS 全部安装成服务并实时同步”。这是增加多个真源，不是融合。
- “写一个全新 `MemoryManagerV3` 再造 SQLite+FAISS”，没有对照成熟源码/之前 W2 的必要性。
- “把每次模型回答都自动认为真实记忆，连续强化”。会变成自我循环。
- “既然是 AGI，就必须全量录屏常驻和每条消息都反思”。不保证有用，未来应留按事件/预算/隐私分级决策能力。
- “所有旧功能从零重写，测试只看能不能启动”。不允许跳过兼容已有用户记忆与来源对应关系。

## G. 判断完成，而不是无限讨论

交付给 Codex/Opus 的每一个机制必须包含：精确上游 URL+commit+license、输入输出与错误边界、推荐复用形态（直接复制小函数/局部移植/重构替换）、需要保留的现有 Atlas 代码、最小反例、实测是否通过及尚未知因素。只有“有 GitHub 链接”“看起来先进”不得进入施工账单。
