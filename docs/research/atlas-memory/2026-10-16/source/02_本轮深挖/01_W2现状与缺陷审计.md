# Atlas 记忆代码现状：不能再把 W2 当作没做

## 1. 静态核实范围

通过已连接 GitHub 读取 `unicorn-Y/Atlas` 的 `memory-v1`、`memory-w2-api`、`memory-w2-ui`；只读，没有在用户主机运行任何命令。当前仓库状态是远端分支快照，不代表 `D:\Atlas` 当前部署。`memory-v1` HEAD `9ace88c5731ed8be6dd7406d758161236938e2de`。W2-A 与 W2-B 相对 memory-v1 均 diverged，不能合并验收记录。

## 2. 源码层面的高风险 / 功能不足

### A. Dream 全局 checkpoint 可能使未成熟分组永远错过重新整理（高优先级待重现）

`dream.py::_episode_groups(library, checkpoint)` 先筛 `entry.at > checkpoint`；同时只选 `len(distinct_days)>=3` 或当次明确写出同名主题的 group。`run_dream` 在这些 group 完成后将 `.dream-state.json` 中全局 checkpoint 设为 **now**。一个只出现两天、尚未点名的长期项目若当天未满足分组规则，其旧两条记录未来不会再进入从 checkpoint 之后的扫描，因此以后即使第三天新增记录，也只见第三天这一条。这是静态可推导的风险，正式施工前必须用 3 日期顺序（每天 dream 一次）写回归。

> 正确解法不是泛滥写第三套 Dream：借 ReMe `DreamState.changed_paths / checkpoint_paths / failed_paths`，将“已消费的 source event IDs”和“待重新评估的不足条件组”分别持久化；只对成功处理过的证据/分组推进水位，且支持重新计算。

### B. 项目关联依赖 `entry.trigger` 的名字（误合并/漏合并风险）

`_episode_groups` 对每条经历的 trigger 候选作为安全化 `name`，同条经历可能同时属于多个候选组，而这些 token 不一定是 project identity。比如工具名、文件名、主题词可能产生错误项目页。**项目 ID/仓库 ID/设备 ID/任务 ID 应来自稳定上下文；触发词仅用于检索候选**。

### C. 来源回溯定位不够强

`sources.py::open_ref` 把 `session@timestamp` 拆开，然后在该会话里找时间最接近的 user 消息。并发轮次、同秒消息、历史数据迁移、时间缺失可能打开错误片段。核心契约应改为 `source_id → session_id / message_id / tool_call_id / event_id + offset`；旧 `session@timestamp` 仅作为迁移兼容。

### D. 每次 Dream 整体重写派生页面；增量性和证据保真有限

Dream prompt 把既有页面交给模型，解析四类 Markdown，输出时明确保留手改/用户说的记录，其他旧派生内容依赖模型重述而不保证保留。正确演进方向是结构化 Claim upsert / supersede / dispute，并保存引用。Markdown 页面可以继续作为可编辑视图，不宜同时又是唯一事实级真源。

### E. “verified = tool ok”与“任务确实完成”不能混淆

任务经历有 `verified` 布尔值，但验证来源依赖 runtime 标志及模型整理结果。是否真正通过目标验收，不可以仅凭命令返回码 0，可能有错误预期、错误路径、无关测试、被 mock 的脚本。强证据至少保存 `check_type + check_ref + expected + observed + scope + verified_by`；Skill 晋升必须引用此类证据。

### F. W2 还没有形成明确的运行中检索策略

W1 召回主要在对话前。W2-A 改进“已有记忆查询”的质量，但还不等于 MemOS 的 `turn_start/tool_driven/sub_agent/decision_repair/skill_invoke` 五个触发点都融入运行时。这个差别直接影响 Atlas 是否会在连续工具失败后主动想起经验。

## 3. 严格禁止的重复派工

- **不要派工**“新建梦境整理系统”“新建向量检索文件”“新建项目时间线界面”；先拉取 W2 工作树做三方 diff、厘清哪些已实现、测试哪些不全、如何合并。
- **不要派工**“从零写混合检索排序”；对照 `hybrid.py` 与 Hindsight `fusion.py` 同轨迹测后选一个。
- **不要派工**“新建 Skill 生成器”；先追 `skill_sleep.py` 调度、harvest、回放、接受/回滚、Skill 实际调用，再看 MemOS eligibility/ReasoningBank 能增益什么。
- **不要按提交分支名称判断已生产运行**；必须从 Atlas 真实 runtime/配置和导入路径确认。

## 4. 立即可做但无需触动真实数据的最小验证

1. 对 W2 dream 建 3 天连续增量测试：day1/day2 各 Dream 成功但未归类；day3 满足多日门槛应生成唯一项目页，源引用完整。
2. 对出处建立两条同秒 user messages，验证 open 精确找到正确 `event_id` 而不是邻近者。
3. 对重复触发词建立来自两个不同 workspace 的 episode，检验是否跨项目误合并。
4. 对 `verified` 建“tool exited 0 但目标验收失败”的反例，不能晋升 Skill。
5. 评估 `memory-w2-api` 和 `memory-w2-ui` 合并冲突与接口类型对齐；不要拿两份独立 PASS 冒充 E2E。
