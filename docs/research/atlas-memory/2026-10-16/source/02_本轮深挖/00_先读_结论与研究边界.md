# Atlas 原生长期记忆：多模态目标、源码吸收与下一步裁决

日期：2026-10-16｜性质：研究与架构设计，不是已完成开发或本机性能验收

## 你确认的目标（不得偏移）

1. **Atlas 自己的一套记忆系统**。深入研究优秀项目如何实现提炼、检索、巩固、纠错、跨会话连续性、经验学习、Skill 晋升和多模态事件关联；直接复用可靠源码或移植算法，统一改造进 Atlas 原生语义和生命周期。不是插很多彼此独立的记忆插件。
2. **开发中的 Atlas 不需要迁就旧架构**。Markdown、Git、SQLite、现有 Python 模块、前端页面、runtime 都可比较、合并、替换。兼容性是迁移成本，不是天条；复杂性和许可风险同样不能无视。
3. **最终覆盖聊天、任务、工具、桌面、浏览器、手机、语音，以及跨设备连续经历**。
4. **视觉、语音、手机感知：本轮完整研究和设计接口，暂不实施**。这三个方向不是“取消”，也不是“以后再决定事件模型”。未来可研究 3060 6GB 笔记本承担一部分感知处理，但不提前假设它能跑动哪种具体模型。
5. **拒绝迎合式结论**：不能因“类脑”“AGI”“图数据库”“SOTA”或高 star 数就判断更好。证据分三级：代码明确存在 / 其他作者宣称 / 在 Atlas 相同任务实测胜出。前两级不能冒充第三级。

## 本轮真正的新成果

- 重新核对 Atlas `memory-v1` 与 **W2 两个并行分支**。`memory-w2-api` 含 `hybrid.py`、`embed.py`、`sources.py`、`dream.py` 和 API；`memory-w2-ui` 含浏览器 UI。分支相对 `memory-v1` 为 diverged，不能假定已合并或目前运行的 D:\Atlas 使用它们。
- 发现 **W2 dream 检查点存在疑似漏整理**：只按时间门槛筛新经历，少于三个不同日期且未直接点名的项目可能暂不组成分组；但运行结束更新检查点到当前时间，后续增加新证据时旧记录可能永远不再进入该轮。需用跨日回放证实，不能当“已发现实测 bug”。
- 查到 **AMA-Agent** 发布的 `construct.py` 与 `retrieve.py`：保留轨迹、提取状态和可选因果图；检索后有证据充分性判断和分支追查。这补充了原有只看向量召回的研究盲区。
- 查到 **MIRIX auto_dream** 的并发隔离：按 owner 串行化整理，多进程模式还使用数据库 advisory lock，避免同一批 session 被双重提炼。Atlas 后续如要多设备/多 worker 整理，同样必须解决此类竞争。
- 查到 **LongMemEval-V2 AgentRunbook-C V2** 的学习策略：历史“以前检索对过”的方法只能作为线索，当前回答必须重新拿到本次证据，不能把老结论当直接证据。
- 明确 **screenpipe 主仓 2026-06-09 改商业源码许可证**，可以合法研究其架构，但不能不看授权就复制现行代码；老 MIT 版本的许可范围另论。OpenViking 主仓 AGPLv3；这两者均不能与 MIT/Apache 项目混为一谈。

## 主体裁决（非物理数据库定案）

**一条原始证据链 + 多类可修正的派生记忆 + 场景检索 + 可验证技能**。这不是预设 1 个 SQL 库或 1 个大服务，而是统一的语义协议。合理拆分：

- Evidence：原始观察/执行轨迹，有稳定 ID、设备/应用、时间/来源、内容指针；不把 LLM 摘要当原话。
- Episode：按任务/活动产生的有边界的经历，而不是“每天一条涵盖所有事”。
- Claim/Entity/Relation：可纠错、双时间、证据追溯的动态世界状态；相同事件的重复摘要不算多个独立来源。
- Policy/Procedure/Skill：跨不同经历提炼策略，验证后才晋升执行资产；复用 Atlas 已有 SkillOpt 而不重造第二套晋升器。
- Recall / MemoryUseTrace：在对话开始、出错、子任务切换、调用技能和验证前主动召回；记录“看到/引用/实际使用/行动结果”，便于反向优化。
- Future modality envelopes：预留视觉、音频、手机的媒体引用、语义事件和权限边界；**不建设实际采集器**。

## 不应误导用户的三件事

1. **这些是研究成果，不是已安装到 Atlas 的新记忆系统**；没有在用户的 Windows 机器上运行候选代码、复现实验数字。
2. **不应保证“全部项目已经找齐”**；本轮重点是具体机制、代码定位、复用成本和隐藏风险。记录的竞争方案均有待相同轨迹复现。
3. **存得越多≠会做事越好**。衡量标准应是：正确修复任务、正确回忆决策依据、更新过期事实、避免重复失败、用户能纠错和删除、不同设备/Agent 语义一致。
