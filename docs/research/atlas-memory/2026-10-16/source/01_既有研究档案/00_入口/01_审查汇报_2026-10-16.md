# Atlas 记忆系统｜资料整合、真实性复核与缺口报告

**整理日期：2026-10-16**  
**对象：** `unicorn-Y/Atlas` 的 `memory-v1` 记忆链路与此前 2026-10-14~15 的 A/B/C 调研、查漏、源码评审和 Opus 交接材料。  
**目标：** 让 Atlas 不只是存储个人资料，还能在合适时机回忆自己和用户的经历，基于真实操作结果逐渐改善做事能力，之后复用已有 Skill 系统。  
**证据边界：** 本次把既有研究文档逐份归档、交叉审查，并通过已连接的 GitHub 读取当前代码与结果文件、比较分支。**没有在用户 Windows 电脑上重新运行 Atlas，也没有新做全网项目普查或第三方实测**。2026-10-15 的旧源码评审已经不能直接视作最新版状态。

## 一、先给结论

1. **资料还在，足以进入有选择的施工；但绝不能称作“所有记忆技术已经完整查完”。** A 产品/用户线和 C 学术线主要是研究线索，B 有 13 维概述、部分真正的源码定位；只有一部分项目达到了可精确定位函数和提交的层次，几乎没有独立的 Windows/中文/成本实测。详见原始覆盖矩阵。
2. **旧版 Atlas 缺陷清单已过时。** 2026-10-15 原审查基线为 `memory-v1@7826e91`；2026-10-16 再核对，`memory-v1@9ace88c5731ed8be6dd7406d758161236938e2de` 相比该提交向前 28 次提交，已含 W0 与 W1。不能继续把“完全不会记录经历”“没有持久队列”等当作当前代码事实。
3. **现状更像“可靠性基础 + 简易情景摘要”，离会主动联想、能追溯因果、在操作中用旧经验解决问题的记忆体系还有距离。** W1 做到了按日/会话整合最近经历和有限工具步骤，但不是完整事件图/多阶段任务过程，也没有持续反馈的技能晋升闭环。
4. **别重复造 Skill 引擎。** `core/atlas/evolution/skill_sleep.py` 已有从 Atlas 会话挖掘重复任务、通过 SkillOpt 验证学习技能的实现入口。需要对接记忆证据与现有 Skill 生命周期、确认是否实际按计划执行；不能并行再引入一套竞争的 MemOS 自动晋升后端。
5. **下一步最值钱的是 W2“执行中动态召回”和关联召回**，随后再做真实事件归因、巩固、成功失败经验、既有 Skill 闭环；不是继续下载几十个名称像海马体的项目。

## 三、Atlas 到底做了什么：按最新版重新判定

**来源：** [当前 `memory-v1` HEAD](https://github.com/unicorn-Y/Atlas/commit/9ace88c5731ed8be6dd7406d758161236938e2de)、[W0 结果](https://github.com/unicorn-Y/Atlas/blob/memory-v1/docs/memory/W0-RESULT.md)、[W1 结果](https://github.com/unicorn-Y/Atlas/blob/memory-v1/docs/memory/W1-RESULT.md)、[Opus 本地审查](https://github.com/unicorn-Y/Atlas/blob/memory-v1/docs/memory/REVIEW-OPUS-PACK-2026-10-15.md)。GitHub 比较显示 `memory-v1` 比旧 `7826e91` 领先 28 个提交；当前相对 `main` 领先 322 个提交（这个差值只是分支关系，不说明桌面软件部署了哪个版本）。

| 能力 | 复核后状态 | 证据/局限 |
|---|---|---|
| 开始对话时加载用户、当前事项、Atlas 自己的记忆 | **已有基础** | `run_phases.py` → `library.recall()` → 系统上下文；不是人脑全量记忆 |
| Markdown/Git 可查看改写事实 + SQLite/FTS 检索 | **已有基础** | 统一记忆主库；原始 engine 会话与日志保留独立证据源 |
| 人工改动 `text/value` 不一致、旧值回灌 | **W0 有针对修复与 9 项测试记录** | 不是说绝对再无冲突；未在这次复跑 |
| 事实有效期读前过滤、召回配额、先过滤再排名 | **W0 有针对修复** | 需要用真实长期负载衡量排序和延迟 |
| 遗忘后清当前正文/索引/记忆库 Git 历史 | **W0 做了范围内修复** | 不代表 engine 原会话、备份、远端副本已完全擦除；结果报告明确范围边界 |
| 后台观察持久队列和重试 | **W0 有实现** | 尚需确认生产进程重启/升级场景；不能简单写“完全不丢” |
| 记录“上次聊过/做过什么” | **W1 已实现简易情景摘要** | `经历/YYYY-MM-DD.md`，按同 session、同一天合并；并非独立多事件的全链路记录 |
| 记录工具执行过程及结果 | **W1 部分** | 最多收集 30 个步骤/记忆条目仅保留最后 8 个步骤，成功验证标记可能依赖运行时上报；不能等同于完整可复查 trace |
| 排除自动审计/临时 workspace 的污染 | **W1 已加跳过规则** | 真实旧日记只 `--dry-run` 预览过待清理项；旧数据的实际清洗状态本次未验 |
| 跨会话回忆上次话题 | **W1 有一次主机真模型冒烟** | 4 句的短测例成功；不能从这推断跨月、多人、多任务准确率 |
| “睡眠”式增量提炼、跨周自动巩固 | **尚未有 W1 正式完整实现证据** | W1 结果明确每晚经历整理暂缓；不能把日记累积当作有效巩固 |
| 按事件联想、处理相似问题但区分不同原因 | **不完善/待专项实现** | 目前主要 FTS/关键词/话题匹配，缺有来源的关联证据和失配约束 |
| 工具报错/阶段切换时实时回忆往事 | **W2 待实现证据** | 搜索有 `memory_search` 工具≠系统主动在错误现场调用；`memory-w2-plan` 分支目前与 `memory-v1` 的所查库文件一致 |
| 子 Agent 的经历归并及共享权限 | **不完善** | 过去 worker 自动读写被隔离；W1 结果写明 worker 归并暂缓 |
| 成败经验归纳→策略→技能复用与退役 | **已有 `skill_sleep.py` 入口，但记忆到技能闭环未证实** | 要核夜间调度、验证、反馈是否贯通，而不是新建第二个晋升系统 |
| 记忆与定时/条件提醒的真实执行闭环 | **尚缺统一证据** | 自动化能力存在≠前瞻记忆/意图状态机已连接 |
| 视觉/音频/手机操作历史的情景级索引 | **尚无统一可验机制** | 需要媒体引用、时间绑定、应用/窗口环境和按需回看；不等于每帧截图都塞到模型中 |

**关键时间线：** 10 月 15 日交接包和 Opus 审核时，旧版缺陷确实存在；随后 W0 和 W1 有施工、测试及合并痕迹。W1-RESULT 在其最初编写时写“没有合并到 `memory-v1`”，但截至本次比较，`memory-v1` 与 `memory-w1` 已相同，说明那句“未合并”是**历史时点描述，不是当前分支状态**。

## 四、为什么用户感觉 Atlas 记忆仍很简陋

### 1. 它当前更擅长回答“记住了哪句话”，不擅长回答“为什么当时这么做”

事实条目与每天一条经历可满足浅层个人化，但一次修复任务通常需要：目标、环境版本、失败尝试、对应错误、验证手段、最后修法、仍然没解决的问题。当前简易 episode 把数次步骤压成少量短文本，跨任务关联不充分。真实例子：“上次修过一个 502，今天这个 502 是不是相同原因？”光靠相同关键词既可能漏掉相关经验，也可能误用旧修法。

**应补：** 事件/阶段 ID → 原始日志引用 → 任务成功/失败/未验证 → 相关 episode 链接；召回结果可按需回溯证据。不必重复保存完整运行日志。

### 2. “存进去”和“工作时想起来”还是两回事

对话开头召回只能覆盖第一个问题。Atlas 干几分钟、开了多个工具、换工作目录、发现错误时才可能需要过去经验；此前注入的上下文往往没有这段具体经历。

**应补：** `turn_start / tool_error / stage_change / before_verification / worker_result` 等少量触发点，统一轻量检索与适用环境校验；先低成本检索，再决定是否调用 LLM。优先处理 W2。

### 3. 它还不能稳健地“从干活中学习”，且可能跟已有 Skill 重复

`skill_sleep.py` 是重要资产，但“入口代码存在”不是“可靠从经验中形成了新技能”。缺省需要知道每条技能的来源操作、在哪些条件成功或失败、什么时候已过期、如何选择调用、调用后怎样把结果反馈回记忆。重复造 MemOS skill engine 会导致两套不一致的技术路线。

**应补：** 现有 SkillOpt 消费 episode / outcome 的适配、真实工具验收条件、负例和版本边界、最低证据门槛、试用与退役反馈；改现有入口而非推倒重做。

### 4. “有记忆”并不是“有长期认知连续性”

用户身份、进行中的 Atlas 项目、尚未完成的承诺、历史决策的依据、模型/设备切换、子 Agent 接手时的条件，都属于不同类别。把它们混在同一份日记或全部常驻 prompt，成本高且容易互相污染。

**应补：** 稳定身份/偏好、项目状态、短期任务与承诺、情景经历、操作策略和技能各有检索入口；源头权限与用户编辑权统一管理。无需上来建十个数据库。

### 5. 没有对记忆“真的帮助做对事”的闭环评分

现有报告和 W0/W1 结果主要验证写入、过滤、短对话召回。这些很必要，但不代表记忆真正提升了 Atlas 的工作质量。

**应补：** 三组真实任务：隔天找回一次多工具修复过程；同故障再次发生时少走弯路；看起来类似但根因不同的故障不会错套旧经验。每组比较有记忆/无记忆的任务完成质量、错误调用和额外耗时，保留最短可靠证据。

## 五、资料真正还缺什么：按价值排序

### A 线｜产品/真实用户
- 中国大陆、日/韩/全球产品的**可复查记忆行为**和独立投诉样本仍不均衡：豆包、Kimi、腾讯元宝、通义、DeepSeek、猫箱/星野/筑梦岛等不能只列名字。需要产品版本、功能如何持久化、用户能否改/删、主动唤起是否冒犯、真实投诉原文和日期。
- Siri、Gemini 接多个应用的数据查询、Microsoft Recall 屏幕历史、真正长期持久记忆是**不同机制**，有些文献混称“记忆”。闭源服务端工作流一般不可证实，不应把 UI 行为推成内部算法。
- 用户抱怨 Top20 主要是定性分类，不是“高频统计”；要算出现频率，必须独立样本与去重分母。

### B 线｜开源/源码
- **第一轮有 18 项的 13 维概述，但多数不是全源码级审计。** 第二轮增加很多候选；10 月 15 日交接包对 ReMe、MemOS local plugin、OpenClaw、A-MEM、ReasoningBank 等高优先项目做了更深的源码定位，但没有等价地覆盖全部其它候选。
- 重点未充分核实或需结合 Atlas 重新裁决：`Mastra Observational Memory`、`OpenViking`、`Honcho`、`MIRIX`、`LangMem`、`MemSkill`、`SimpleMem/EvolveMem`、`Redis Agent Memory Server`、`Graphiti`、`Hindsight`、`Cline/Roo`，以及多 Agent 记忆的证据流。不是说都值得集成，只是资料尚不够强到直接排除或引用其质量数字。
- 多数缺 Windows 可安装性、中文实体/检索表现、内存/额外 token、异常重启、实际删除链路、license 精确文件、最近 issue 是否修复的核对。
- `EverMemOS/EverOS` 属同一主线更名/迁移，`EverAlgo` 是子算法库；`StructMem/EM2Mem` 可能同仓，`Memora` 有同名不同项目。旧版来源已提醒，必须防重计数。

### C 线｜论文/评测
- 早期中心是“长问答记忆”，行动任务维度跟不上。应优先严读、尝试小样例映射：`MemoryArena`、`DolphinBench`、`MemSkill`、`PersonaMem-v2`、`LongMemEval`、`MemoryAgentBench`、`OP-Bench`、`MemSecBench`，把**回忆准确、适用时机、行动收益、失效抑制、运行成本**分开打分。
- 作者报告的准确率或资源开销未在 Atlas 固定模型、相同输入预算下复现；论文逐篇审稿争议、公开代码、数据许可和用户中文案例仍缺。

### D 线｜本机 Atlas / 使用证据（优先级最高）
- **实际主机在用哪个分支和构建版本**、当前记忆目录的积累数量、失败任务队列、索引大小、检索延迟；GitHub 有代码不等于桌面端已加载。
- 自动测试产生的 14 条历史日记 `--dry-run` 标识，是否已经在主机真实数据中完成清理仍未见复核。
- 长任务跨天、并行子 Agent、同名不同故障、手改后巩固、真遗忘在多个历史副本之间的效果，缺连贯现场案例。
- 技能学习脚本是否被实际调度、产出了什么文件、多少有真实验收、不适用何种版本，缺闭环记录。

## 六、推荐推进路线（非“一次写完”大任务）

| 顺序 | 只做的事情 | 借谁的机制，不整体安装 | 证明它有用的最小验收 |
|---|---|---|---|
| **0｜核实当前版本** | 核桌面运行版本/记忆目录，复核 W0/W1 是否在用；归档真实数据快照 | Atlas 自己 | 新会话复述上次真实任务、重启队列和历史页同样可用 |
| **1｜W2 执行中主动召回** | 工具错误+阶段转折触发有上限的经历检索；防重复；能引用过去的证据 | MemOS `retrieve.ts` | 过去修过的故障自动想起；相似不同因不乱套 |
| **2｜经历结构和关联** | 多阶段 episode、事件/工具/版本证据指针、关系与时间有效性 | A-MEM、ReasoningBank 的证据形式；可选 StructMem | 能讲清步骤、为什么失败/成功、哪里没有验证 |
| **3｜有检查点的巩固** | 按新增事件批量提炼、只处理变化、纠错不复活、后台低优先级执行 | ReMe dream 状态机 | 重启后继续，不重复做；旧错不复活 |
| **4｜打通 SkillOpt** | 从真实成功/失败片段产生候选技能，在现有技能系统评估、复用、降级 | MemOS L2/Skill 规则 + Atlas `skill_sleep.py` | 相似新任务少试错，失效技能不继续推荐 |
| **5｜持续性和多模态** | worker 归因、计划/承诺/条件提醒、截图/ASR/UI 证据引用 | MIRIX、Hindsight、Atlas 工具链 | 换会话/设备/执行者仍接得上，能回溯真实依据 |

**刻意不推荐：** 一次把 Mem0、Graphiti、EverOS、MemOS、ReMe 全部作为独立运行时部署；立即改造成多服务多数据库；把模型内部的 Titans/HOPE/DeepSeek Engram 当作现成外接记忆插件；为凑覆盖数装所有仓库；为验收增加大量与记忆效果无关的测试。

## 七、给下一个审查或执行 Agent 的交接顺序

1. 先看本报告以及 `00_开始这里.md`；确认上述“W0/W1 已施工、代码在 `memory-v1`”的新事实。
2. 依次读 `06_Atlas源码与架构/01_Atlas实际链路与缺陷证据.md`（**旧基线**）、`06_Atlas源码与架构/03_统一架构与分阶段任务书.md`（**提案**）、`07_Opus交接/README_阅读顺序与边界.md`（旧审核说明）。
