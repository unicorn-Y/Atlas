# 资料缺口、真正需要用户决定的问题、下一轮研究任务

## 当前研究边界（2026-10-16）

已完成：旧 A/B/C+两版交接成果再利用，新增源码级核查（Hindsight fusion、ReMe dream、MemOS local-plugin retrieval/eligibility、Graphiti 时间字段与边冲突、Mastra OM、Mem0、A-MEM、ReasoningBank、MIRIX、memU），新增 SimpleMem/EvolveMem、LongMemEval-V2、AMA-Bench、Claude-Mem、OpenViking L0/L1/L2、第三方记忆对照索引和评论。已区别“原仓代码存在”和“本人复现实测”。

**尚未完成：** 不能声称已经检索到全球所有记忆项目；尚未对所有仓库逐个阅读完整调用链；没有下载/跑 Windows 依赖树；没有本机中文 benchmark / 连续数周生活与 coding task；没有对闭源服务端做逆向或完整实现还原。因此当前是“新版研究与选型设计阶段”，不能冒充最终胜者已经确定。

## 研究缺口按重要性

1. **写入真实质量**：Hindsight、Mem0、Mastra、ReMe 的不同提取提示词在中文、多轮、反问和反讽中的差异；原始工具输出污染率。
2. **关联和时间**：Graphiti vs Hindsight vs A-MEM，哪种关系模型在 Atlas 的目标/软件版本/故障引用上最好；双时间数据何时失效。
3. **实测部署**：Hindsight full/slim、Graphiti 后端、embedding/reranker、Windows/本机显卡 12GB、CPU/RAM/API 时间费用。
4. **技能真正成功**：现有 `skill_sleep.py` 的状态、复用概率、验证回归，是否已经被调度；与 MemOS L2/EvolveMem 有无重叠。
5. **多模态**：MIRIX 新旧分支、视觉事件到摘要、屏幕变化去重、摄屏隐私与活动索引、音视频证据时间戳。
6. **跨 Agent 共享**：多个模型或设备对同一事实是否采用单一范围/项目授权；写入冲突和离线合并处理。
7. **记忆 UI**：需要用户像编辑知识库一样修改事实、追溯源头、冻结、纠正、撤销和查看技能自动学习原因。
8. **人工用户评价**：不能拿 Reddit 匿名小样本、“作者自报提升 30%”冒充真实大规模用户结论。

## 真正需要用户拍板的问题（先研究，只有实施时会阻塞）

**Q1：性能与能力权衡。** 你是否同意“记忆效果优先、对话/工具执行尽量保持低延迟，允许非交互时批量重处理”的默认假设？如果愿意付出更高成本/复杂环境换效果，应扩大候选到 Postgres+重型图索引、后台模型整理；如果偏重极低延迟和无常驻服务，则应让 SQLite 单机方案有优势。

**Q2：原始记忆范围。** 除聊天和工具行为外，是否默认记电脑屏幕、浏览器浏览历史、手机事件与实时语音？全量留存和事件触发摘要对应截然不同的磁盘/隐私/成本。

**Q3：多 Agent 记忆共享权。** Codex / Atlas / Claude 等应共享同一项目事实与经历吗？若其中一个模型推断错误，是否允许自动修改全局长期记忆？默认建议：能共享引用，派生结论有来源；跨代理写入候选，用户确认事实需要证据或用户本人表态。

**Q4：现有历史兼容。** 既有 Atlas `data/memory` 和 MemoryOS 的数据，迁移时保留原样和历史轨迹，还是允许彻底重新导入、重新提炼？我建议保留迁移备份、然后新系统按事件逐步重算，旧库不会永远保留为运行时依赖。

## 推荐给执行 Agent 的下一批研究任务（研究，不改主仓）

1. 固定 Atlas 运行版本与真实数据/日志；完整绘制 session/tool/skill/memory 调用链；交出真实可复现的 20 个记忆任务，避免主观选型。
2. 在独立试验环境取 Hindsight、Graphiti、ReMe、MemOS local-plugin 的锁定版本，按文件和函数标注重用成本、许可证、可裁剪依赖，并分别用一条原始日志运行最小机制。**不安装多套常驻产品在 Atlas 主机上。**
3. 同一回放在 A/B/C 三种架构和 R0/R1/R2 检索通道横向跑；记录正确率与延迟、token、磁盘、纠错/遗忘。
4. 再选数据底座并写原生模块图和迁移文档，然后 Codex 分阶段执行，按结果决定保留/淘汰代码。

**研究不是止于这一轮。** 新项目会不断出现，任何“所有的记忆项目已经全部查完”都是不严谨的说法。应维护固定证据等级、可重复验证的候选池，而非越堆越长的模糊名称清单。
