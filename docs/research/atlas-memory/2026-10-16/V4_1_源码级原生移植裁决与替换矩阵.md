# Atlas 记忆系统 V4.1 — 源码级原生移植裁决与替换矩阵

> **定位：V4 的实施深化，不是另做一套 Memory，也不是已施工证明。日期 2026-10-16。** 原文历史研究仍在 `source/`，旧 V4 ZIP 保持原归档。读本文件时并行阅读 `V4_2_原生施工任务书与接口契约.md`。

## 0. 按用户原话固定施工目标

2026-10-16 用户提供的聊天记录 `chatgpt_personal_selected_2026-10-16 (1).zip` 再次明确：

> “研究他们的记忆系统，有用的拿过来改改用，研究他们的方式构造方法什么的，是做atlas自己的记忆系统……就像拿过来翻译成自己的东西。”

并强调 **不能为兼容还在开发中的 Atlas 旧架构而放弃更好实现**。

翻译为明确的施工操作：
- **直接移植成熟的源码及对应测试/提示词/数据格式**，只保留所需的算法核；同为 Python 时避免逐行重写，TS 源码要有行为对等的 Python 移植或独立 TS 内核，依据依赖大小决定。
- **替换旧实现允许且鼓励**，但应清楚迁移旧数据和仍在使用的调用入口，不允许在旧模块旁做第二个长期真源。
- **Atlas 是唯一记忆主体**；Codex/Claude/子 Agent 可充分修改 Atlas、执行任务。统一记忆不等于把外部 Agent 关入沙箱，也不等于第三方模型输出就自动具有事实证明力。
- **视觉/音频/手机**现在完成数据事件协议、接口预留和未来上游研究，**暂不做采集与部署**。
- 成功标准不是“移植了 N 个项目”，而是 Atlas 再碰类似任务时更少重复探索、能找原始证据、改正旧记忆、用到以前成功的策略/Skill。

### 重要修正（避免再次误判）

1. **Atlas 已有稳定消息 ID！** `core/atlas/engine/session_sync.py` 的 `message_uid`、`latest_session_message_id`、`session_message_evidence` 与 `append_session_message` 已经存在。问题是 W2 `sources.open_ref` 仍靠 session@timestamp 模糊回查；修适配而非制造第二套 UID。
2. **Atlas 的 SkillOpt 不是完整的原生行为记忆系统！** `skill_sleep.py` 实际从 `engine/state.db` 的用户会话提炼 SessionDigest，调用外部 `skillopt_sleep.cycle.run_sleep_cycle`，配置 `auto_adopt=True`。该脚本不能直接证明 tool-step 能得到精确 reward、夜间任务在生产调度已经持续运行，或每个 Skill 真实有效。
3. **MemOS 本地插件是 TS 2.0.16-beta.1**，直接将其完整 TS 包嵌入 Atlas Python 后端，可能带来 Node 构建、双套数据存储和运营复杂性；只移植成熟场景检索/eligibility 纯函数及 prompt/test 更符合用户“翻译为原生”。
4. **ReMe 本身以文件目录+文件 catalog 为原理**：如果原样复制所有服务层容易与 Atlas 的 SessionDB/EventLog/项目文件重复。要借其 Extract→Integrate→Finish 核心，按 Atlas 事件 ID 事务推进。
5. **Hindsight RRF 是简明的排名组合，不是记忆正确性的保证。** 源码中的 `RetrievalResult/MergedCandidate/ArmScores` 强依赖 Hindsight 类型，Atlas 的 adapter 只需最少字段。
6. **Graphiti 的 valid/invalid 与 created/expired 是不同含义的时间**，不能全部叫 memory_updated_at；`episode` 的推断因果边也不应当等于工具日志证明的因果。
7. **LongMemEval-V2 的逻辑轨迹 fingerprint 保留 `id`**（本轮直接读取），所以“同内容不同运行 ID”的实际去重必须扩展它，不应声称现成算法自动做到跨运行去重。

## 3. 开发语言/数据底座的真正选型原则

Atlas 后端已经是 Python，前端 Electron/React。为保持原生：
- Python 来源且算法依赖小（ReMe schema、Hindsight fusion、AMA get/find、Graphiti temporal rules）：**优先迁 Python 实现与测试**，不要为了调用几段逻辑启动上游服务器。
- MemOS 来源是 TS：仅将 **独立判定/排序/预算** 以有输入输出夹具的方式翻译成 Python。若某个 TS 子树不可拆且行为显著更好，需列出真正依赖闭包，比较嵌入 Node 子库与 Python 翻译，不凭“原生”偏好强制重写复杂内核。
- 用户要求的是 Atlas 自己控制生命周期、状态、API、文件和扩展演化，**不是强制每一行代码自研**。保留 NOTICE/LICENSE/来源表，并标注代码与上游 commit。
- 底层 SQLite、Markdown、Postgres、图服务之间尚无实测裁决；先把**数据模型及读写契约定义成可替换**，迁移先建立单向校验与读旧兼容，不允许为了选 DB 重写现有功能三遍。
- **推荐暂定**：现有 `engine/state.db` 提供 canonical session / message；记忆库自己的 schema 提供派生 Episode/Claim/Embedding/索引；项目/用户 Markdown 可以继续做人读视图，但不再成为唯一不可回溯的证据来源。这个设计取决于真实数据源是否完整，不是数据库的终局裁决。

## 4. 三种做法的对照（防“假原生化”）

| 做法 | 是否符合用户要求 | 原因 |
|---|---|---|
| 直接把 ReMe/MemOS/Hindsight 当独立长记忆服务，Atlas 走 HTTP | **否**（除非仅用于隔离基准实验） | 第二长期真源、双向同步和上游版本不受控 |
| 看完源码只写提示词让模型“参考某项目自行实现” | **否** | 核心算法实质重新发明，可能丢失测试和边界规则 |
| 提取具体源码函数+行为夹具，最小改造接 Atlas 原接口，淘汰旧重复分支 | **是** | Atlas 自主掌控原生代码/数据，复用成熟实测机制 |
| 为了删掉所有第三方版权，从头改写一份功能同等源码 | **否** | 速度和质量差，仍有许可/著作权问题 |
| 为了迁就旧 Markdown 页面牺牲记忆证据和纠错能力 | **否** | Atlas 仍处开发期，允许迁移旧架构 |
| 用已验证的基础设施（SQLite FTS5 等）保存自己设计的逻辑内核 | **是** | 自有记忆系统不等于自己重新实现数据库 |

## 5. 直接复用的边界与最小正确性

每个移植块必须有：
- **Source map**：上游仓库 + commit + 文件 + 起源函数 + 对应 Atlas 文件/函数。
- **兼容检查**：上游输入输出样例在 Atlas 适配后表达同一语义，不需建立巨型测试框架；只测真正关键行为。
- **唯一真源**：新增模块是否生成可再追溯的 source_event_id？若不能则只保留为缓存或临时推断。
- **失败可恢复**：独立消费进度记录只前进成功来源，重试不得重复出现同一 episode/claim。
- **版本与许可证**：不把复制开源代码改个类名就当自己全权原创。明确 `docs/third_party/atlas-memory-port/NOTICE.md`（施工时建立），MIT 保留版权及许可，Apache-2.0 保留许可证和 NOTICE/修改说明；插件子项目许可单独确认。
- **不带入上游的“宿主”**：没实际需要时不要搬进其 HTTP/MCP 服务、数据库迁移脚本、UI 或遥测 daemon。
