## Source verification and limits

Clones are under `D:/Atlas-x-prep-sources/x2-x3-x6/`. Exact SHA, commit date, license, and inspected file list are in `evidence-x2-x3-x6.json`. Stagehand is MIT, Browser Use is MIT, Playwright is Apache-2.0; confirm each vendored file's current header and dependency notices at implementation time. These are implementation candidates, not permission to copy dependencies wholesale.

- [Playwright browser contexts](https://playwright.dev/docs/browser-contexts) support isolated state; persistent profiles must be handled as an explicitly owned persistent context, not silently shared between tasks.
- [Stagehand v3 reference](https://docs.stagehand.dev/v3/references/stagehand) documents server caching for `act`, `extract`, and `observe` on Browserbase; this is cloud-only and has no effect in local mode. It is not a local authenticated-profile cache.
- [Browser Use repository](https://github.com/browser-use/browser-use) includes CDP connection, local profile, downloads and upload examples/tests. [Persistent cloud profiles and sessions](https://github.com/browser-use/browser-use/blob/main/skills/cloud/references/sessions.md) describe cloud profile persistence; implementation must separately prove Windows local Chrome profile locking and recovery.
- [xAI official workflow guide](https://docs.x.ai/grok-bot/skills-routines-and-automations) establishes demonstrative learning as a reviewed draft; the exact availability can be gradual. No automatic learned-workflow install is justified by that guide.
- Perplexity's [Windows Personal Computer page](https://www.perplexity.ai/en-GB/hub/products/computer-for-windows) documents local Windows files, apps, Comet, voice, and user-scoped folder access. Its [Mac setup page](https://www.perplexity.ai/personal-computer-setup) separately documents phone pairing/remote approvals. Keep those platform claims separate; no generic cross-platform 24/7 property is inferred.
- Claude's [local versus remote connectors guidance](https://support.anthropic.com/en/articles/11725091-when-to-use-desktop-and-web-connectors) makes local desktop access dependent on the computer running Claude Desktop/local extensions. Do not claim a cloud schedule can reach an offline local desktop/profile.

## Atlas and Hermes inspection findings

Atlas currently wires `ComputerUseRuntime` into the agent tools (`core/atlas/agent/__init__.py`), with implementation in `core/atlas/tools/computer_use.py`; CUA and UIA helpers are separate under `core/atlas/capabilities/computer/`. Browser Use is currently a separate capability adapter. This is the consolidation target: one lifecycle and policy owner, browser and desktop backend adapters underneath, rather than three agent-facing tool families.

Hermes' CUA driver is an upstream implementation reference. The inspected Hermes `gateway/pairing.py` is DM-user pairing, not desktop-device trust, and must not be represented as device pairing. The browser artifact store is scoped one-shot transfer, not persistent artifact sync.

## Pre-implementation decisions and acceptance

1. Select a single runtime owner in the existing Atlas `AgentBackendHost`/tool registry/session. Runtime identity is `(atlas_session_id, device_id, profile_id)`; browser profiles use per-profile exclusive locks and never serialize cookies into task/event logs.
2. Start browser tasks with a visible authenticated Chrome/CDP attach when requested; retain the same profile after Atlas restart. Headless ephemeral contexts remain explicit task-scoped contexts. Ask the user to finish login/CAPTCHA in the attached browser, then resume the same task/profile.
3. Use UIA element references and readback as first choice for native controls; escalate to foreground screenshots/vision when UIA has no usable tree or state. Actions carry target device/window, expected state, timeout, and idempotency key. Multi-monitor/DPI coordinates are device-local and normalized with monitor metadata.
4. Fake acceptance: fake CUA and fake CDP servers cover runtime selection, a11y/vision fallback, window targeting, duplicate command idempotency, process death/restart, stale browser lock, user handoff/resume, download/upload metadata, and event order. No live accounts or user profile.
5. Real acceptance: isolated disposable Windows user/profile and local test site; attach persistent authenticated profile, perform UIA action and browser DOM action, force Atlas runtime restart, resume same profile/task, download/upload fixture, handle a JS dialog, ask for manual CAPTCHA/login handoff, and verify no credential/cookie leaks in logs/artifacts. Include two monitors and non-100% DPI, and both background and foreground escalation. Record actual Windows build, display topology and evidence paths.

Blocked/unverified: concurrent real Chrome use against an existing personal profile, unattended Windows login/sleep/lock behavior, exact Windows desktop session policy, and image/vision parity are not confirmed by repository inspection and remain explicit real-acceptance gates. CUA-specific license and driver versions must be rechecked from the exact vendored/installed artifact before porting.
