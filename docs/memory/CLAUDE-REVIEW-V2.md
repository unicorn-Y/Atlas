## 一、GPT 方案里对的部分（保留）

1. **主体和委派规则**：Atlas 是唯一的记忆主体；外部 Agent 权限全开；派活时先给一份上下文，执行中可以再要；做完的结果收回 Atlas。
2. **原文是证据，派生的东西都能重建**；用 SessionDB 现成的 `message_uid`，不另造 ID。
3. **W2 的缺陷清单**：Dream 漏组、无模型时删队列、失败 3 次后冻结、向量没调度、出处靠时间戳、工具步骤只留 30×200 字。我逐条看过代码，**都是真的**。
4. **执行器说「完成了」不算验收**：exit=0 不等于目标达成，要有工具输出或测试结果。
5. **召回出来的东西不能当新事实写回去**（防自我强化）。Atlas 其实已经有一半：`sanitize_context` 会把 `<memory-context>` 块从原文里剥掉。
6. **当前任务的进度和长期记忆分开存**。
7. **视觉、语音、手机现在只定事件字段，不写采集代码**。
8. **不另做一套技能系统**，接现有的 SkillOpt。

## 二、GPT 方案的问题

### 问题 1：漏掉了和 Atlas 最直接可比的两家（最严重）

你给 Atlas 定的目标是「每个细节都比最强那家好」，对标的是 CC、Codex、Hermes、OpenClaw。GPT 的研究重心却在学术项目上，Codex 的记忆管线和 Hermes 的记忆钩子一次都没深挖过。这两家的源码就在手边，而且正好解决你抱怨的那几件事：

- **Codex 两阶段记忆**（源码在主机 `D:\_deliverables\官方拆解汇总\Codex-Official\03-SOURCE\codex-rs\memories`）：
  - **第一阶段**：会话空闲后逐个提炼，产出详细的 `raw_memory`、一份会话回顾，再加原文指针。数据库里有抢占租约，失败按退避重试；没东西可记就什么都不写。
  - **第二阶段**：一个整合 Agent 先看 git diff，知道这次哪里变了，再去改三样东西：`MEMORY.md`（可以 grep 的手册）、`memory_summary.md`（常驻的短总览）和 `skills/`。用户手改的内容要求保留下来。
  - **读取**：常驻短总览，模型自己搜手册，再往下钻到原文，总共 4–6 步以内；**执行中连续出错就重查一遍**。
  - **按使用排序和遗忘**：回答末尾带一个引用块，里面的会话 ID 会让 `usage_count` 加 1；第二阶段按使用次数挑输入，超过 `max_unused_days` 没用过的就淘汰。
- **Hermes MemoryProvider**：每轮前召回、每轮后写入、子 Agent 结果回收、会话结束、记忆写入通知，都是现成的接口。GPT 设计的 ContextBroker、场景召回、结果回收，在这里本来就是这一组钩子。

### 问题 2：和你「透明记忆库」的要求冲突（这是新发现）

GPT 把 Markdown 降级成「只读展示视图，不再作为来源」，真正的数据放在 `source_events` 表、`MemoryClaim` 主谓宾三元组和 Entity/Link 关系里。这样会有两个后果：

- 你在界面上改了一条记忆，改的只是投影。下次重建会被覆盖，除非再写一套反向同步。
- 你看到的是数据库渲染出来的结果，不是它真正记着的东西。

Codex 的做法正好相反：**记忆本身就是 Markdown 文件，放在 git 里，第二阶段要求保留用户的手改**。这和你要的透明记忆库完全吻合。Atlas 记忆库本来就是 Markdown + git，正合用。

### 问题 3：数据结构过重，中文生活记忆拆主谓宾很脆弱

- 新建 `source_events` / `processed_events` 两张表 + Claim 双时间 + Entity/Link，这是知识图谱路线。
- 拿中文的日常和工作经历去拆主谓宾，很容易拆错。Graphiti 自动让旧事实失效这一套，GPT 自己引用的 issue 里就有大面积误判。
- 双时间只对少数「会变的状态和偏好」有用。在 W0 现有事实条目（已经有 `at`/`until`）上补两条规则就够了：「被谁取代」，以及「你的纠正优先于推断」。

### 问题 4：对上游的理解有偏差（已对照源码）

- **ReMe Dream**：检查点按「文件路径 + 修改时间」记（`file_catalog` 的 `st_mtime`），默认只扫最近 2 天；整合是给每条提炼结果配一个带读写工具的 Agent，逐条合并进已有笔记（新建 / 佐证 / 细化 / 更正）。GPT 写的「按事件 ID 推进的处理账本」是它自己加的，ReMe 里没有。ReMe 真正值得学的是**逐条增量合并，不整页重写**。
- **MemOS 召回**：`tool_driven` 是模型调用记忆工具时才触发，不是工具出错时；出错时触发的是 `decision_repair`，失败次数到阈值才召回。而且 MemOS 核心是 TS 写的，把 5 个场景翻成 Python 的 RecallRouter，工作量不小。Codex 一句「连续出错就重查」加上模型自己检索，就能拿到同样的效果。

### 问题 5：召回思路落后一代

GPT 的做法是系统主动把 top-k 结果塞进提示词，再加 RRF 融合、证据充分性判断。主动推送正是「明明记着却答错」和「过度个性化」的来源。现在最强的做法是**很短的常驻总览 + 模型带预算自己拉取 + 能下钻到原文**。Atlas 已有 `memory_search` 和 `open_ref`，离这一步只差一点。

### 问题 6：没有「有没有用」的闭环

GPT 只在概念上提到要追踪用没用，没有落地机制。Codex 的「引用块 → 使用次数 → 挑选和淘汰」可以整套搬过来，代码量很小。

### 问题 7：过程太重

- 60 个文件、3 个压缩包（1.5MB 二进制进了 git）、V3/V4/V4.1/V4.2 四层互相覆盖。
- 实验 E01–E06、关卡 G0–G4、20–50 个任务的对比跑分。
- 另起一个 `native/` 包，迁移期间会和 `library/` 并存，等于 Atlas 里同时有两套记忆系统。

这些和你「提速、少测试、靠使用和日志排查」的规矩冲突。

## 三、GPT 和我上一版都漏掉的

1. **「只认亲口说的」取消以后，可信度怎么分。** 不能一视同仁，每条记忆标上来源：你说的 > 工具观察到的（命令输出、测试结果）> Atlas 自己的推断。冲突时高的赢；推断出来的东西在界面上要看得出是推断。
2. **联想。** 两边都没给出又轻又透明的联想办法。我的建议是在记忆页之间用 `[[链接]]` 互相指（我自己的记忆就是这么做的，也是 A-MEM 的思路），建索引时把链接当成图，召回时顺着链接多看一跳。这样不用建 Claim 图，你打开文件也能看懂。
3. **3,298 条 Skill 目录怎么和记忆合流。** GPT 只说了一句「应该合流」，没给做法。我的建议是：技能目录单独建一个可检索的索引，不进记忆库；记忆里只记「哪次任务用了哪个技能、效果如何」；第二阶段整合发现的技能候选交给 SkillOpt 把关。
4. **子 Agent 和外部 Agent 的会话也要提炼。** Codex 的第一阶段只处理主会话，不处理子会话。Atlas 的执行器很多，需要 `on_delegation` 把子会话收回来，一起送进第一阶段。

## 四、我对上一版评审的更正

- **压缩不是丢细节的主要原因**：Atlas 压缩时会把原文归档。`on_pre_compress` 降为锦上添花，用途是把相关记忆写进压缩摘要。
- **「只认亲口说的」取消后**，M3 的提炼范围改为：你的事实和偏好、做过的事、决定和理由、踩过的坑、没做完的事、观察到的环境变化，每条带来源等级。
- 其余结论经这次源码复核，**保持不变**。
